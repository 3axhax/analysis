# Доставка на рабочий сервер

Production всегда разворачивается из `master`, если пользователь явно не указал другую ветку. Источник файлов — репозиторий после `git pull`, а не ручная передача исходников.

## Подготовка и Git

1. Выполнить `git status --short`, отделить изменения задачи от чужих файлов, проверить diff на secrets и generated artifacts.
2. Выполнить проверки затронутых компонентов и `git diff --check`, закоммитить изменения.
3. Выполнить `git fetch origin --prune`. Актуализировать локальный `master` из `origin/master` через fast-forward, слить рабочую ветку в `master`, разрешить конфликты и проверить объединённый код.
4. Выполнить push рабочей ветки и `master`. Убедиться, что локальный HEAD `master` совпадает с `origin/master`. При конкурентном обновлении повторить fetch и согласовать изменения; force push запрещён.

Пример для уже существующей основной ветки:

```sh
git fetch origin --prune
git switch master
git merge --ff-only origin/master
git merge <рабочая-ветка>
# Проверки объединённого кода
git push origin <рабочая-ветка>
git push -u origin master
```

## Сервер

1. Подключиться по SSH. Не выводить учётные данные или содержимое env-файлов.
2. Проверить серверный checkout, ветку, `git status --short`, compose project/config, mounts и текущие образы. Локальные изменения разобрать до pull; не сбрасывать их и не прятать автоматически в stash.
3. Получить ветки, переключиться на `master` и выполнить:

```sh
git fetch origin
git switch master
git pull --ff-only origin master
git rev-parse HEAD
git rev-parse origin/master
```

При первом создании серверной ветки использовать `git switch --track -c master origin/master` вместо обычного switch. Смена ветки не должна перезаписывать локальную конфигурацию.

4. Убедиться, что build context указывает на этот checkout. Проверить compose-конфигурацию без печати интерполированных secrets. Собрать затронутый сервис из файлов после pull и обновить только его. Для клиента при согласованном manifest:

```sh
docker compose -p analysis -f <проверенный-manifest> build client_analysis
docker compose -p analysis -f <проверенный-manifest> up -d --no-deps --no-build client_analysis
docker exec nginxProxy nginx -t
docker exec nginxProxy nginx -s reload
```

5. Проверить HTTPS, главную и изменённые страницы, assets, API health и фактический результат изменения. Проверить, что незатронутые сервисы не перезапущены. Зафиксировать опубликованный commit и проверки.

## Данные и очистка

Явный запрет пользователя на дополнительные backup соблюдается. Он не разрешает удалять рабочие данные. Без отдельного согласования не удалять Docker volumes, uploads, дампы, конфиги, сертификаты или каталоги, используемые mounts/compose. Для разрешённой очистки сначала проверить контейнеры, образы и mounts; удалять только подтверждённо неиспользуемые ресурсы. Очистка не должна перезапускать сервисы. Удаление старых образов убирает возможность отката к этим образам.

# AGENTS.md

## Назначение

Этот репозиторий — веб-сервис «Проанализируй» для предварительной расшифровки лабораторных анализов. Пользователь вручную вводит показатели или загружает PDF, указывает пол и возраст, после чего сервис сопоставляет значения с референсными диапазонами и выводит заранее подготовленные интерпретации. Результат носит справочный характер и не является диагнозом.

Работай от кода, локальной PostgreSQL и обезличенных fixtures. Персональные данные из медицинских PDF, сохранённые результаты, дампы БД, учётные данные и session tokens считаются чувствительными данными. Не выводи их содержимое в терминал, ответы, логи задач или Git.

При сверке описаний с методичкой пользователь просит сохранять её формулировки, не добавлять собственные обобщения, повторы показателя и статуса или лишние оговорки; допустимо смягчать категоричность. Не применять текст к условиям, которых источник не задаёт.

Пользователь просит исправлять найденные ошибки и опечатки по умолчанию, без дополнительного запроса; медицинские смысловые изменения по-прежнему проверяй и документируй, а неоднозначные случаи уточняй.

Пользователь сообщил, что сохранённые измерения в локальной БД не имеют для него ценности; при согласованных изменениях справочников допустимо перепривязывать их к корректному показателю. Это не распространяется автоматически на production и не отменяет защиты чувствительных данных или правил миграций.

Перед работой всегда выполняй `git status --short`. Репозиторий может содержать незавершённые изменения пользователя; не перезаписывай и не форматируй их без необходимости.

## Стек и структура

- Client: React 19, TypeScript, Vite 7, Redux Toolkit, React Router, i18next, Tailwind CSS.
- Server: NestJS 11, TypeScript, Sequelize 6 / `sequelize-typescript`, PostgreSQL.
- PDF parser: FastAPI, `pdfplumber`, Uvicorn; отдельный Python-контейнер.
- Production proxy: Nginx с TLS, SPA client и проксированием `/api/` в NestJS.
- `client/src`: Feature-Sliced-подобная структура `app`, `pages`, `widgets`, `features`, `entities`, `shared`.
- `server/src`: NestJS-модули по сущностям; основные домены — показатели, типы анализов, единицы, возрастные интервалы, нормативы, результаты, описания, переводы и авторизация.
- `python-microservice/app.py`: извлечение таблиц и текста из PDF.
- `docker-compose.dev.yaml`: dev-стек с bind mounts и портами приложения.
- `docker-compose.yaml`: production-подобный стек с Nginx и собранными образами.
- `sqlDump/` и `testData/`: локальные игнорируемые каталоги с потенциально чувствительными данными; не считай их fixtures, пригодными для публикации.

Отслеживаемые `server/.env` и `client/.env` должны содержать только безопасную для репозитория конфигурацию. Локальные `.postgres.env`, `server/.development.env` и `client/.dev.env` не копируй в задачи и ответы. Не печатай значения переменных окружения; для диагностики достаточно имён переменных и проверки соединения.

## Доставка на рабочий сервер

- Когда пользователь просит выполнить операцию на рабочем сервере, самостоятельно выбери интерфейс текущей сети и подключись к `72.56.1.204` по SSH по [инструкции для macOS](DEPLOYMENT.md#подключение-по-ssh-с-macos). Определяй интерфейс перед каждым новым подключением. Используй существующую SSH-конфигурацию и штатную проверку ключа сервера. Для подключения не требуется добавлять или удалять системные маршруты.
- Основная production-ветка — `main`. Другую ветку разворачивай только по прямому указанию пользователя.
- Обязательный порядок: проверить и закоммитить изменения → получить актуальное состояние origin → слить рабочую ветку с `main`, разрешить конфликты и проверить результат → push рабочей ветки и `main` → подключиться по SSH → в серверном checkout переключиться на `main` и выполнить `git pull --ff-only origin main` → собрать и обновить затронутые контейнеры → проверить публичные endpoints.
- Источник поставки — Git checkout после pull. Не доставляй исходники через Base64, копирование отдельных файлов, SCP или патчи поверх старого релиза. Не собирай production из несогласованного дерева.
- Перед pull проверь серверную ветку и `git status --short`. Не перезаписывай локальные конфиги, secrets, сертификаты, uploads и пользовательские изменения; не применяй `reset --hard`, `clean` или автоматический stash. Разбери расхождения до переключения контейнеров.
- Проверяй фактические compose project/config, build context, bind mounts и image. Они должны соответствовать согласованному checkout; старый manifest может ссылаться на прежние исходники. Обновляй только необходимые сервисы, без ненужного перезапуска backend/БД/PDF. Учитывай startup migrations перед запуском backend.
- Сверяй опубликованный commit с `origin/main`; фиксируй commit, результат проверок и фактический путь checkout. Push и merge сами по себе не означают публикацию.
- Дополнительные backup делай только согласно применимым правилам и запросу пользователя; явный запрет пользователя имеет приоритет. Очистку выполняй только по запросу, после проверки использования ресурсов. Не удаляй volumes, данные, конфиги, сертификаты, uploads или каталоги, используемые контейнерами.
- Подробный порядок: [DEPLOYMENT.md](DEPLOYMENT.md).

## Поток данных

1. Client загружает справочники показателей, типов анализов, единиц, пола и возраста через REST API.
2. Пользователь вводит показатели вручную либо отправляет PDF в `POST /result/fromFile` (лимит 10 MiB, ожидается PDF).
3. NestJS передаёт буфер в `python_pdf_parser:8000/extract-tables`; Python обрабатывает страницы 1–5 и возвращает таблицы и извлечённый текст.
4. `ParseFileService` сопоставляет строки с `analysisPoint.translationParsing` либо RU/EN-названиями, извлекает первое положительное число меньше 3000 и возвращает найденные показатели клиенту. Автораспознавание является подсказкой: пользователь должен проверить показатели и выбрать единицы.
5. `POST /result/save` проверяет возраст в днях и пол, создаёт `analysisResult` с `ageInDays`, затем сохраняет распознанные показатели в `analysisResultPointData`.
6. `POST /result/get` получает результат по случайному 40-символьному hex `resultId`, находит по `ageInDays` все применимые записи `ages`, сопоставляет значения с интервалами и подбирает описания, все условия которых совпали.
7. Client показывает результат на `/result/:resultId`; ссылку можно скопировать и открыть без авторизации.

Никогда не трактуй результат алгоритма как медицинский диагноз. Изменения сопоставления, диапазонов, единиц и текстов интерпретации требуют предметной проверки и тестов на граничных значениях.

## API и авторизация

- Публичные маршруты: справочники для формы, `POST /result/save`, `POST /result/get`, `POST /result/fromFile`, `POST /auth/login`, `GET /i18n/:lng/:ns` и health/root.
- Административные CRUD-маршруты для возрастов, единиц, показателей, описаний и переводов защищены `@Roles('ADMIN')` и `RolesGuard`.
- Глобальный `AuthGuard` только пытается найти пользователя по Bearer token и всегда возвращает `true`; фактическое ограничение доступа обеспечивает только `RolesGuard` на явно размеченных endpoints.
- Session token — случайный 32-символьный hex, хранится в `users-sessions` и в client `localStorage`. В текущей модели нет срока действия, logout/revocation и уникального DB-ограничения на token.
- Результат доступен любому, кто знает `resultId`; это capability-link, а не приватный кабинет. Не логируй и не публикуй такие ссылки.
- CORS сейчас отражает любой origin и разрешает credentials. Не расширяй публичную поверхность API; при изменениях авторизации добавляй негативные тесты для anonymous, USER, ADMIN, неверного и отозванного token.

## Модель PostgreSQL

Локальная БД: `analysisdb`, PostgreSQL 18. Основные группы таблиц:

- Справочники: `ages`, `gender`, `analysisType`, `analysisPoint`, `analysisPointUnits`, `translation`.
- Связи: `analysis_type_point`, `analysis_point_units`.
- Нормативы: `analysisPointIntervalValue`, интервалы с границами, включительностью, статусом и источником.
- Результаты: `analysisResult` и дочерняя `analysisResultPointData`.
- Интерпретации: `analysisResultDescription`, `analysisResultDescriptionCondition` и `analysisResultIntervalDescriptionCondition`.
- Доступ: `users`, `roles`, `users-roles`, `users-sessions`.
- Служебная таблица `migrations` учитывает самописные startup migrations.

Связи результата:

```text
analysisResult
  -> ageInDays, по которому подбираются все применимые ages
  -> gender
  -> users (nullable; фактического FK в локальной схеме нет)
  -> analysisResultPointData[]
       -> analysisPoint
       -> analysisPointUnits

analysisPoint
  <-> analysisType через analysis_type_point
  <-> analysisPointUnits через analysis_point_units
  -> интервалы по age + gender + unit + source

medicalSource
  <-> ages через medicalSourceAge, если источник ограничен по возрасту

analysisResultDescription
  -> conditions[]: analysisPoint + связанные интервалы
```

Схему меняй миграциями, а не ручным SQL как способом доставки. NestJS при старте выполняет `MigrationsService.onModuleInit()`: создаёт таблицу `migrations` и запускает идемпотентные `ALTER TABLE` для известных изменений. Поэтому даже обычный запуск server-контейнера потенциально изменяет схему.

Согласованные изменения в локальной БД можно выполнять без дополнительного подтверждения и предварительной резервной копии. Перед миграцией, восстановлением дампа, очисткой результатов или массовым CRUD обозначь область изменений и выполни read-only проверки. После операции проверь ограничения, число затронутых строк и возможность отката. Для production действуют правила доставки на рабочий сервер.

Для read-only диагностики используй агрегаты и каталог схемы:

```bash
docker exec postgresAnalysis sh -lc 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -P pager=off -c "SELECT current_database(), current_user, version();"'
docker exec postgresAnalysis sh -lc 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -P pager=off -c "SELECT table_name FROM information_schema.tables WHERE table_schema = '\''public'\'' ORDER BY table_name;"'
```

Не выбирай и не показывай `users.email`, `users.password`, session token, `analysisResult.resultId`, индивидуальные значения анализов или текст из PDF.

## Критически важная логика

- `AnalysisResultService.saveResult()` выполняет техническую валидацию и сохраняет весь набор исходных измерений атомарно в repeatable-read транзакции. Поиск нормативов/конверсия при save запрещены: отсутствие интервала не блокирует результат и не исключает строки. Ноль разрешён; отрицательные/нечисловые значения, неизвестные point/unit и дубли point дают явную ошибку запроса, а не молчаливый пропуск.
- Измерения хранят точные sourceValue/sourceUnitId/sourceUnitText без calculation/reference fields. Расчёт при GET использует интервалы с учётом единицы, возраста и пола. Значение без подходящего интервала остаётся видимым без статуса. GET ничего не записывает.
- `MigrationsService` запускает зарегистрированные миграции при старте, включая переход к интервальной модели и зачистку старых структур. Миграции с marker выполняются атомарно и защищены advisory lock. Исторические миграции нужны для обновления старых схем и не являются альтернативным механизмом расчёта.
- Aliases — `analysisPointUnits.translationParsing` через `_`, правила — `unitConversionRule`. Перед rollback останови новую версию: startup повторно применит отсутствующий marker. Не удаляй исходные измерения ради отката.
- БД проверяет отдельные FK point и unit, но не проверяет, что unit разрешена именно для point через `analysis_point_units`.
- Интервалы могут пересекаться; условие описания выполняется при совпадении любого связанного интервала, а описание — при выполнении всех его условий.
- Старый редактор нормативов и описаний удалён; новый редактор остаётся отдельной задачей. CRUD переводов состоит из нескольких независимых операций.
- В `getAnalysisResultDescriptionsByQuery()` фильтр строится через `sequelize.literal`; вход типизирован как число, но любые изменения этого кода должны сохранять строгую DTO-валидацию или перейти на bind parameters.
- Python parser возвращает полный извлечённый текст (`all_text`) в межсервисном ответе и включает детали исключений в HTTP 500. Не логируй эти payloads; ограничивай страницы, размер и время обработки.
- Данные разбора `ParseFileService` локальны для запроса; общий счётчик ограничивает параллелизм. Не помещай request-specific findings в поля singleton provider.
- Python проверяет расширение имени файла, NestJS — MIME/type validator. Для защиты необходима проверка сигнатуры/валидности PDF, лимиты сложности и тесты повреждённых/зашифрованных/огромных документов.
- Публичное сохранение результатов не имеет rate limit, TTL и механизма удаления. Не добавляй новые сохраняемые персональные поля без отдельной модели согласия, retention и удаления.

## Проверка изменений

Сборка backend и тестовый Nest App не доказывают, что работающий HTTP API загрузил новый код. После изменения save/get/единиц проверяй обычный endpoint на синтетическом либо явно указанном пользователем результате, выводя только признаки согласованности без значений и capability ID. Если требуется restart dev backend, сначала проверь, какие startup migrations ожидают запуска; затем проверь API и неизменность данных. Не считай один health200 подтверждением версии/медицинской логики.

### Установленная методология тестов PDF-парсинга

Формат DB-results: pointId/name/value/unit/unitId. pointId=analysisPoint.id, unitId=analysisPointUnits.id; unitId обязан быть разрешён для pointId, при unit=null также unitId=null. Старый id не используется. Runtime matcher распознаёт единицу непосредственно после выбранного результата только среди разрешённых units показателя, без преобразования значения и без назначения единственной unit по умолчанию. Отсутствующее/неподдерживаемое/противоречивое evidence оставляет unitId/unit=null; conflicts явно предупреждаются. Прямое сравнение ожидаемых IDs не требует дополнительного mapping, gold не исправляется автоматически ради совпадения.

Следуй текущей методологии в `tasks/0001-improve-pdf-recognition/testing-methodology.md`. Обычные NestJS-тесты используют заранее подготовленные `testData/python-results/` и `testData/DB-results/`, текущий код и текущую локальную БД read-only; `sources/` — исходный эталон. Отсутствующие файлы только отмечаются, не создаются автоматически.

Без отдельного явного запроса пользователя запрещено создавать дополнительные промежуточные «фиксации» реального корпуса: snapshots/копии каталога БД, frozen baseline, отдельные manifest/expected/mapping файлы, контрольные суммы для допуска файлов, отдельные зафиксированные поднаборы или их архивы. Они не должны подменять prepared данные или исключать изменённые файлы из теста. Существующие DB-results содержат pointId/name/value/unit/unitId: pointId=analysisPoint.id назначается независимо от matcher при явной подготовке эталона; тест сравнивает pointId/value напрямую без повторного поиска по имени. Неизвестный текущей БД id явно диагностируется, не переназначается автоматически. Неразрешимость показывается без молчаливого уменьшения знаменателя. Синтетические unit fixtures не являются фиксацией реального корпуса. Метаданные версии кода/времени запуска можно включать в отчёт, не превращая их в новый источник тестовых данных.

Backend:


- неизвестные point/unit, дубли point и пустой набор;

- отсутствие чувствительных данных в логах и ошибках.

## Известный технический долг

- Admin CRUD связанных справочников остаётся без общей транзакции; сохранение результата атомарно.
- Нет полноценной системы миграций с `down`, блокировкой, общей транзакцией и отдельным CLI; миграции запускаются при старте приложения.
- Нет expiration/revocation sessions, rate limiting, TTL/удаления результатов и ограничения доступа владельцем.
- Capability-ссылки результатов публичны; privacy зависит только от энтропии `resultId` и неразглашения URL.
- Интервалы могут пересекаться и учитывают единицу измерения; пересечение LOW и HIGH одного источника требует проверки данных.
- `analysisResult.userId` и `users-sessions.userId` в локальной схеме не защищены FK, несмотря на смысловую связь моделей.
- Нет составного FK, гарантирующего допустимость unit для point в сохранённом результате.
- Python parser возвращает лишний полный текст; эвристическое сопоставление требует регрессионных тестов и проверки пользователем.
- Справочные CRUD обновляют связанные таблицы и переводы неатомарно; rename может рассинхронизировать translation keys.
- В ответе `addNewAnalysisPoint()` поля RU/EN формируются из переменных в обратном порядке; это требует отдельного regression test перед исправлением.
- DTO и контроллеры местами используют слабые типы (`[]`, `any`) и ручную проверку body вместо полной валидации.
- Production-зависимости собираются с известными npm audit warnings; обновления выполняй отдельной задачей с проверкой совместимости, не через безусловный `audit fix --force`.
- В проекте нет содержательных README и покрытия ключевой доменной логики.

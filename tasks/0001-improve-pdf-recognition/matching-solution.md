# Решение по поиску показателей в извлечённых строках PDF

## Резюме решения

Python-извлечение в следующем срезе не меняется. Улучшение выполняется только после него, в NestJS: текущую inline-логику `ParseFileService` нужно вынести в детерминированный matcher, который сначала понимает структуру таблицы, затем ищет показатель, значение и единицу, дедуплицирует одинаковые представления строки и только после этого разрешает кандидатов.

Новый matcher нельзя сразу подменять в рабочем endpoint. Сначала он работает в benchmark/shadow-режиме рядом с legacy matcher на локально сохранённых обезличенных результатах извлечения. Переключение допускается только после сравнения с expected manifest по точности point/value/unit. Количество возвращённых findings само по себе критерием не является.

Рекомендуемый вариант: **структурный matcher с legacy fallback, вводимый через измеримый compatibility gate**. Изменения схемы и данных БД для первого среза не нужны.

## Исходные факты

- На 10 локальных PDF исходный matcher вернул 119 findings из 233 структурно посчитанных строк (51,1%). Это proxy полноты, а не доказанная точность.
- Экспериментальный conflict-aware matcher вернул 72 findings (30,9%): на 47 меньше baseline.
- В эксперименте 66 из 72 findings содержали `multiple_numeric_candidates`, а 7 документов получили конфликт значений.
- Независимая проверка Python-ответа показала присутствие 458 из 465 технических строк (98,5%). В двух документах Python передал 7/7 строк, а NestJS вернул 0 findings; ещё в одном переданы 37/37 строк и также получено 0 findings.
- В БД 67 показателей и 196 записей алиасов. После нормализации выявлено 7 коллизий, затрагивающих 12 показателей; 51 алиас имеет длину не более трёх символов.
- RU/EN fallback фактически не используется: `translationParsing` заполнен у всех 67 показателей. Плоское добавление переводов не увеличило число mentions на корпусе, но резко увеличило число вложенных алиасов.

Следовательно, главный резерв улучшения находится не в Python и не в массовом расширении словаря, а в четырёх местах NestJS: структура колонок, дедупликация extractor-строк, контекстное применение алиасов и разрешение нескольких чисел.

## Почему эксперимент оказался хуже baseline

### 1. Дедупликация выполнялась слишком поздно

Эксперимент сначала превращал каждую строку каждого extractor в самостоятельный finding-кандидат, затем группировал их по `pointId`. Совпадали только пары с полностью одинаковыми `value` и `unitId`; любое расхождение превращало всю группу в `conflicting_values_require_review` и показатель удалялся.

Так одна физическая строка, представленная `lines`, `text` и `coordinates`, могла выглядеть как несколько противоречащих медицинских результатов. Это основная архитектурная причина потери findings.

### 2. Result и reference считались равноправными числами

Роль result-column определялась только по первым пяти строкам каждой отдельной таблицы и не переносилась на таблицу-продолжение или следующий extractor. При отсутствии распознанного заголовка выбиралось первое число после alias. Референсный диапазон, дата, номер примечания и значение результата не имели разных ролей.

Поэтому `multiple_numeric_candidates` было не исключением, а нормой: warning получили 66 из 72 findings.

### 3. Коллизии алиасов обрабатывались глобально

Любой нормализованный алиас, принадлежавший нескольким показателям, полностью исключался из индекса. При этом глобальный warning о наличии коллизий добавлялся в каждый документ, даже если неоднозначный алиас в нём не встречался.

Дополнительно canonical-нормализация и замена визуально похожих кириллических символов выполнялись одним проходом. Такая tolerant-нормализация сама создала или расширила часть коллизий.

### 4. Приоритет алиаса был внутренне противоречив

Индекс сортировался сначала по `parsingOrder`, затем по длине, но выбор «сильнейшего» совпадения использовал длину первого элемента. Короткий высокоприоритетный алиас мог неявно затенить более специфичный длинный алиас.

### 5. Недостаточно данных для решения «лучше/хуже»

Baseline выбирает первый подходящий кандидат и потому имеет высокий raw count, но его precision неизвестен. Эксперимент удаляет сомнительные группы и потому имеет меньший raw count, однако без expected point/value/unit нельзя доказать, что оставшиеся 72 результата верны. Сравнение 119 против 72 показывает регрессию выдачи, но не измеряет качество распознавания.

## Целевая архитектура NestJS

### 1. Чистый matcher вместо inline-логики

Выделить модуль без HTTP и БД-запросов, например:

```text
PdfFindingMatcher.match(extraction, catalog) -> MatchResult
```

`ParseFileService` остаётся orchestration-слоем: получает каталог из БД, вызывает существующий Python-сервис и передаёт оба объекта matcher. Это позволит прогонять один и тот же Python-ответ через legacy и новый алгоритм без повторного чтения PDF.

Основные внутренние типы:

```text
AliasEntry       pointId, source, raw, canonicalKey, tolerantKey, risk
TableContext     page, method, nameColumn, resultColumn, unitColumn, referenceColumns
LogicalRow       page, normalized cells, extractor sources, context
PointCandidate   point, value candidate, unit candidate, evidence, score, warnings
```

### 2. Сначала структура таблицы

Для каждой таблицы определить роли колонок по двум группам признаков:

- заголовки: показатель/name, результат/value, единица/unit, референс/reference;
- форма данных: доля текстовых имён, одиночных чисел, range-выражений и unit-like значений в колонке.

Контекст переносится только в пределах той же страницы и совместимой сигнатуры колонок. На следующую таблицу или страницу он переносится, если число колонок и типы данных совместимы и новый явный заголовок не найден. При недостатке доказательств контекст не угадывается.

Строки заголовков и служебные строки не должны участвовать в поиске значений.

### 3. Дедупликация до matching и конфликтов

Из доступного текущего Python-контракта нет bbox, поэтому первый срез использует безопасный semantic fingerprint:

- page;
- canonical-нормализованный плоский текст строки;
- последовательность нормализованных ячеек и числовых токенов.

Полностью одинаковые строки разных methods объединяются в один `LogicalRow`, а список sources сохраняется как evidence. Для немного различающихся представлений объединение допускается только после совпадения point alias, выбранного result-value и unit; одного похожего текста недостаточно.

Конфликтом считается не отличие raw extractor rows, а наличие двух разных высокоуверенных result-values для одного point после структурного разбора. Повторение одного значения разными extractors повышает уверенность.

### 4. Слоистый alias index

Индекс строится без миграции из существующих данных:

1. `translationParsing` — primary aliases.
2. RU/EN-переводы — exact-cell fallback, только если primary alias в строке не найден.
3. Короткие, collision и confusable/OCR-варианты — contextual aliases.

Для каждой строки сохраняются два ключа:

- `canonicalKey`: NFKC, пробелы, регистр, пунктуация и дефисы;
- `tolerantKey`: отдельный дополнительный ключ с confusable folding.

Tolerant-совпадение не должно побеждать canonical exact match. Алиас не удаляется глобально из-за коллизии: неоднозначность разрешается по конкретной строке через exact name-cell, result-column и допустимую единицу. Если контекста недостаточно, строка становится ambiguous и не заполняет форму автоматически.

Короткий алиас допускается только как отдельный token/ячейка имени и только при наличии структурно определённого result-column. `parsingOrder` используется последним tie-breaker, а не раньше специфичности и структуры.

### 5. Разбор значения

Порядок выбора:

1. Ячейка явно найденного result-column.
2. Одиночное число в ячейке, соседней с name-cell, если другая соседняя ячейка однозначно является unit.
3. Число после alias в одноклеточной строке — compatibility fallback.
4. Legacy second-cell fallback только как низкоуверенный кандидат в shadow/benchmark, а не как безусловный победитель.

Range, дата, возраст, номер примечания и числа из reference-column исключаются из result candidates. Поддерживаются decimal comma/dot, scientific notation и inequality с сохранением warning. Универсальный порог `0 < value < 3000` не используется для выбора показателя: медицински необычное, нулевое или отрицательное число не искажается и не становится другим значением. Политика его показа/сохранения должна проверяться отдельно.

### 6. Единица

Unit определяется только из unit-column или из однозначного токена рядом с выбранным result-value и только среди units, разрешённых данному point. Наличие у point единственной разрешённой unit само по себе не доказывает, что документ использует именно её.

В первом срезе достаточно in-memory словаря безопасных вариантов написания. Массовая правка БД и отдельная aliases-таблица не нужны. Если совпадения нет или их несколько, `unitId` остаётся `null`.

### 7. Scoring и решение

Score должен быть разложен на объяснимые признаки, а не быть одной скрытой эвристикой:

- источник и точность alias;
- exact name-cell против совпадения во всей строке;
- наличие result-column;
- однозначность числового кандидата;
- подтверждение unit;
- согласие нескольких extractors;
- штрафы за короткий/tolerant/collision alias и fallback без структуры.

Для каждого point выбирается кандидат только если он прошёл минимальный порог и имеет достаточный отрыв от второго кандидата. Порог и margin фиксируются тестами, а не подбираются непосредственно на всех десяти PDF. При конфликте старый `first candidate wins` не применяется молча.

Поскольку текущий frontend игнорирует warnings и сразу заполняет форму, ambiguous-кандидаты нельзя возвращать в `findings`. Их безопасные агрегатные количества можно вернуть в `stats`; отдельный review UI требует другой задачи.

## Compatibility gate и тестирование

### Эталон

Создать ignored локальный manifest для каждого файла:

```text
expected: pointId, normalized numeric value, expected unitId|null
```

Manifest и сохранённые Python-ответы не коммитятся, если содержат медицинские данные. Runner выводит только агрегаты и категории ошибок, без имён файлов, point names, значений и raw rows.

Главные метрики:

- point precision/recall;
- exact value accuracy среди правильно найденных points;
- unit accuracy/coverage;
- число ambiguous и причины miss;
- document success/partial rate.

`findings / структурные строки` остаётся диагностической proxy-метрикой.

### Автоматические synthetic regression tests

Обязательные случаи:

- result и reference в разных колонках;
- таблица-продолжение без повторного заголовка;
- одна физическая строка от `lines`, `text` и `coordinates`;
- один point с действительно разными результатами;
- переставленные name/result/unit колонки;
- короткий алиас в name-cell и тот же token в unit/служебном тексте;
- два point с collision alias;
- canonical и tolerant/confusable match;
- decimal comma/dot, scientific notation, zero, negative, inequality, range и дата;
- одна, несколько и отсутствующая разрешённая unit;
- несколько страниц и повтор одного point;
- неизвестный point, пустая таблица и неизвестный extractor method.

### Условие переключения

Новый matcher сначала запускается только в тестовом runner. Затем возможен shadow-режим без изменения ответа endpoint. Он становится основным только если:

- point precision не ниже baseline;
- point recall не ниже baseline;
- exact value accuracy не ниже baseline;
- unit не назначается при неоднозначности;
- нет регрессии concurrency/privacy-контрактов;
- категории оставшихся ошибок объяснены и покрыты тестами.

Числовые целевые проценты задаются после создания expected manifest. До этого обещание «распознавать все файлы» непроверяемо.

## Этапы реализации

1. **Benchmark harness.** Сохранить локальные Python responses, создать ignored expected manifest и зафиксировать метрики legacy matcher.
2. **Characterization.** Дополнить тесты текущего matcher, включая его ошибочные, но фактические правила: первая ячейка, первое значение, первый point, порог 3000.
3. **Pure matcher.** Вынести normalizer, alias index, table context, numeric parser и resolver в отдельные TypeScript-файлы без изменения endpoint.
4. **Structure + dedup.** Ввести `LogicalRow`, роли колонок и дедупликацию до создания кандидатов.
5. **Layered aliases + units.** Добавить контекстные алиасы и безопасный unit matching без изменения БД.
6. **Benchmark comparison.** Получить агрегатный отчёт legacy/new и классификацию misses.
7. **Shadow/cutover.** После выполнения compatibility gate переключить matcher feature flag; legacy оставить как быстрый rollback на один релиз.

Предлагаемый минимальный срез:

```text

server/src/analysisResult/pdf-finding-matcher.ts
server/src/analysisResult/pdf-finding-matcher.spec.ts

```

Python, схема PostgreSQL и данные справочника не меняются. Если позже потребуется регулярно управлять lab profiles/aliases через admin UI, нормализованную таблицу алиасов следует оформить отдельной задачей с backup, миграцией и rollback.

## Решение по вариантам

- Не продолжать прежний conflict-aware matcher точечными правками: порядок его стадий неверен, и локальные исключения сделают поведение ещё менее объяснимым.
- Не возвращаться к legacy как к итоговому алгоритму: он полезен как контроль и rollback, но его `first candidate wins` не отличает результат от reference и не измерен по precision.
- Не расширять массово `translationParsing`: на текущем корпусе проблема преимущественно не словарная, а структурная.
- Не использовать fuzzy distance/LLM/внешние сервисы: для коротких медицинских обозначений это увеличивает false positive и ухудшает воспроизводимость.
- Принять структурный matcher с legacy compatibility gate как следующий реализуемый срез задачи 0001.

## Уточнение решения: hybrid compatibility layer

После первого corpus-прогона structured matcher принято предметное уточнение:

- короткие canonical English aliases являются сильным сигналом медицинского параметра в русскоязычной лабораторной таблице;
- для point с единственной разрешённой unit допустимо предположить эту unit, но источник предположения должен оставаться явным;
- полезные свойства исходного first-cell/second-cell алгоритма следует сохранить как fallback, а не воспроизводить его внутри сложного scoring.

Реализуемое упрощение:

1. Structured matcher остаётся первым слоем и имеет приоритет по point.
2. Canonical English alias длиной до трёх символов принимается в первой ячейке либо name-column без обязательного header context. Collision и tolerant keys сохраняют строгие ограничения.
3. Legacy matcher добавляет только point, отсутствующие в structured результате; такие findings получают `legacy_compatibility_fallback`.
4. Если у point ровно одна разрешённая unit, hybrid назначает её с `unit_assumed_from_single_allowed`. Из нескольких units автоматически не выбирается ни одна.
5. Resolver не смешивает structured и legacy candidates в общей балльной конкуренции: это делает приоритет детерминированным и сохраняет быстрый rollback.

Hybrid не отменяет compatibility gate. Raw count используется только как proxy полноты; переключение default требует expected point/value/unit и проверки precision/recall, exact value accuracy и unit accuracy. Результаты corpus-прогона и решение о runtime mode находятся в `test-results.md`.

# Финальный тест распознавания параметров PDF

> Этот документ фиксирует исторический сквозной тест NestJS matcher от 2026-08-30 на корпусе из 14 PDF. Более поздняя проверка только Python extraction на расширенном корпусе из 17 документов не пересматривает выводы о NestJS matching и хранится отдельно в `python-test-result.md`.

## Параметры проведения проверки

| Параметр | Значение |
|---|---|
| Дата и время | 2026-08-30 19:53:47, UTC+05:00 |
| Корпус | 14 текущих PDF из `testData/`: `01.pdf`-`14.pdf` |
| Python endpoint | `POST /extract-tables`, страницы 1-5 |
| NestJS endpoint | `POST /result/fromFile`, режим `hybrid` |
| Справочник | Локальная PostgreSQL, 67 `analysisPoint`, только read-only запросы |
| Старые результаты | Не использовались; из `test-results.md` взято только оформление |

`01.pdf` и `07.pdf` являются точными копиями, но учитываются как два отдельных входных файла. Проверка содержимого также показала, что переименование PDF не удалило персональные идентификаторы внутри документов. Поэтому в отчёт не включены ФИО, даты, номера, значения анализов, извлечённый текст и raw JSON.

## Методика подсчёта

Для каждого PDF заново определены четыре величины:

1. **Показателей в PDF** - визуально подтверждённые строки лабораторных результатов. Повтор одного показателя в разных extraction-стратегиях Python не увеличивает число.
2. **Ожидается по БД** - уникальные показатели PDF, для которых в текущей PostgreSQL существует соответствующий `analysisPoint`. Два варианта одного показателя в одном документе, например две формы RDW, считаются одним ожидаемым DB-параметром.
3. **Упомянуто Python** - ожидаемые DB-параметры, названия которых присутствуют в таблицах/ячейках свежего `ExtractTablesResponse`, независимо от перестановки колонок и переноса строки.
4. **Распознано NestJS** - фактическое число уникальных `findings` текущего hybrid matcher и реального endpoint `/result/fromFile`.

Процент распознавания рассчитывается как `распознано NestJS / ожидается по БД × 100`. Это количественное покрытие названий показателей. Оно не доказывает правильность выбранного числового значения и единицы измерения.

### Наличие параметров в ответе Python

- все **152 из 152** параметров, которые затем вернул NestJS, присутствуют в Python response: **100,0%**;
- все **242 из 242** ожидаемых по БД параметров имеют упоминание названия в Python response: **100,0%**;
- следовательно, основной разрыв текущего корпуса возникает после extraction, на этапе сопоставления названия/строки с `analysisPoint`, а не из-за отсутствия названий в ответе Python;
- `1 940 raw rows` не являются количеством уникальных параметров: Python намеренно возвращает повторные представления строк из нескольких extraction-стратегий;
- OCR не запускался, поскольку все документы имели пригодный текстовый слой.

## Проверка NestJS

Реальный `POST /result/fromFile` вернул HTTP 201 для всех 14 файлов. Число `stats.matched` во всех ответах совпало с длиной `findings` и с результатом standalone hybrid runner.

| Matcher | Findings | Покрытие относительно 242 expected |
|---|---:|---:|
| Legacy | 150 | 62,0% |
| Structured | 80 | 33,1% |
| Hybrid / текущий endpoint | 152 | 62,8% |

Контрольные агрегаты hybrid:

- 141 из 152 findings содержат предупреждения;
- 72 findings добавлены через `legacy_compatibility_fallback`;
- для 120 findings unit назначена по допущению единственной разрешённой unit;
- 8 findings остались без однозначной unit;
- зафиксированы 22 ambiguous candidate groups;
- ни один документ не получил статус `complete`.

## Вывод

В текущих 14 PDF визуально подтверждено 276 строк лабораторных параметров. С текущим справочником БД сервис должен уметь сопоставить 242 уникальных параметра. Python response содержит названия всех 242 ожидаемых параметров, но NestJS hybrid matcher возвращает 152 findings. Итоговое количественное покрытие составляет **62,8%**, остаточный разрыв - **90 ожидаемых параметров**.

Полное распознавание корпуса не достигнуто. Наиболее заметные провалы: `13.pdf` - 0 из 23 expected, `12.pdf` - 7 из 21, `02.pdf` - 3 из 7, а также `01.pdf` и его копия `07.pdf` - по 11 из 20. Даже строки со 100% количественным покрытием остаются `partial`, поскольку содержат предупреждения о fallback, unit или конфликтующих кандидатах. Для оценки precision, корректности значения и unit нужен отдельный expected manifest `pointId + value + unitId`.

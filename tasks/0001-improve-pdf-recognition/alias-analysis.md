## Текущая модель

`ParseFileService` делит `analysisPoint.translationParsing` по символу `_`, нормализует полученные строки и строит общий индекс. RU/EN-переводы используются только когда `translationParsing` пуст. В текущей БД это fallback-фактически недостижим: `translationParsing` заполнен у всех 67 показателей.

После нормализации алиасы, относящиеся к нескольким показателям, полностью исключаются из поиска. Оставшиеся записи сортируются сначала по `parsingOrder`, затем по длине. При совпадении нескольких алиасов matcher ориентируется на первый элемент отсортированного массива, поэтому приоритет может неявно победить более длинную и более специфичную фразу.

Короткие алиасы нельзя просто удалить: на корпусе 49 из 139 point-document mentions находились только через алиас длиной не более трёх символов. Одновременно такие алиасы имеют повышенный риск совпадения с заголовками, единицами, служебным текстом и другими показателями, поэтому им нужен более строгий контекст.

Текущая замена похожих кириллических символов латинскими применяется ко всей строке, а не только к OCR/mixed-script ошибкам. Она полезна для визуально похожих букв, но уже создаёт или расширяет 4 из 7 нормализованных коллизий. Исходный нормализованный ключ и confusable-folded ключ следует хранить раздельно.

Выводы по корпусу:

- плоское добавление RU/EN-названий не дало ни одного нового point mention в текущих 10 документах;
- два документа с одним показателем не покрываются ни `translationParsing`, ни RU/EN-названиями: им нужен новый проверенный alias, подтверждение отсутствующего показателя в справочнике либо профиль макета;

- большой разрыв между 139 point-document mentions и 72 findings подтверждает, что изменение алиасов без исправления result/reference и дедупликации extractors не решит задачу;
- collision aliases реально встречаются как минимум в трёх документах и сейчас полностью исключаются из matching.

## Варианты модификации

### Вариант A — точечная очистка `translationParsing`

- по expected manifest добавить только подтверждённые отсутствующие варианты;
- разобрать 7 нормализованных коллизий и 17 пар вложенности;
- для коротких алиасов задать обязательный контекст: отдельная ячейка имени, найденная result-column и при необходимости unit;
- удалить дубли и явно валидировать delimiter `_` в admin-операциях.

Плюсы: без изменения схемы и небольшой diff. Минусы: строковое поле не хранит источник, язык, профиль лаборатории и правила контекста; сопровождение остаётся ручным.

### Вариант B — слоистый индекс в памяти

- слой 1: подтверждённые `translationParsing` как primary aliases;
- слой 2: RU/EN-названия только как exact fallback, если primary alias строки не найден;
- слой 3: короткие/OCR/confusable aliases только при выполнении дополнительных контекстных условий;
- неоднозначный alias не удалять глобально, а возвращать ambiguous только для реально затронутой строки;
- scoring сделать явным: source, exact-cell match, длина, result-column, unit/context, extractor confidence и только затем `parsingOrder`.

Плюсы: не требует миграции, сохраняет контролируемый словарь и устраняет глобальные warnings. Минусы: правила остаются в коде, а admin-интерфейс не объясняет их.

### Вариант C — нормализованная таблица aliases

Отдельная сущность может хранить `pointId`, исходный alias, normalized key, source, language, priority, универсальные требования к контексту и active flag. Уникальность следует задавать по нормализованному ключу и области действия, а неоднозначности валидировать до публикации.

Плюсы: аудит и управляемые приоритеты. Минусы: нужна отдельная миграционная задача с backup, dry-run, backfill, constraints и rollback; без expected benchmark новая схема сама по себе не улучшит точность.

### Вариант D — профили конкретных макетов

Вариант отклонён решением от 2026-09-22. Lab-specific aliases, PDF-шаблоны, fingerprints и правила колонок конкретного макета не добавляются.

## Рекомендация

Для следующего среза выбрать **B + точечные действия из A**:

1. Сначала создать локальный expected manifest и классифицировать misses как `alias_missing`, `alias_collision`, `value_conflict`, `unit_missing` или `layout_failure`.
2. Не выполнять плоское объединение всех 300 потенциальных aliases: оно увеличивает пары вложенности с 17 до 229 и не дало прироста mentions на текущем корпусе.
3. Ввести слои primary/exact fallback/contextual short alias и раздельные canonical/confusable keys.
4. Разрешать коллизии в контексте конкретной строки; при недостатке данных возвращать ambiguous, а не выбирать point автоматически.
5. Добавить или изменить конкретные алиасы только после подтверждения expected point для двух непокрытых макетов.
6. После исправления matching повторить benchmark. Вариант C рассматривать отдельно, только если универсальные aliases должны регулярно редактироваться через admin UI.

В рамках этого анализа код, схема и данные БД не изменялись.

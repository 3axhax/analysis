# Ретроспектива и решение по задаче 0001

Дата решения: 2026-09-22.

## Итог задачи

Цель улучшить распознавание показателей не достигнута. На расширенном корпусе Python response содержит названия всех 242 ожидаемых DB-показателей, но NestJS возвращает 150 findings в legacy, 80 в structured и 152 в hybrid-режиме. Прирост hybrid относительно legacy составляет только 2 findings и не подтверждён по точности значения и единицы.

Structured matcher нельзя принимать как улучшение исходного алгоритма. Hybrid также нельзя считать новым рабочим matcher: 72 из 152 findings получены через legacy fallback, 141 finding содержит warnings, а 120 units назначены по допущению единственной разрешённой единицы.

Для текущего корпуса основной разрыв находится после Python extraction, в NestJS-реконструкции строк, сопоставлении названий, выборе result-value и разрешении кандидатов.

## Принятое ограничение универсальности

Хранение шаблонов PDF, fingerprints лабораторий и правил, привязанных к конкретному поставщику или макету, не используется. Такой подход повышает локальную точность ценой универсальности и создаёт отдельный набор правил для сопровождения каждого формата.

Целевой matcher должен работать по общей структуре документа:

- фактическим строкам и ячейкам extraction response;
- определённым из документа ролям колонок;
- общему каталогу показателей и aliases;
- универсальным правилам выбора результата и единицы;
- объяснимым evidence и причинам отказа.

Локальные PDF остаются только закрытым проверочным корпусом. Они не превращаются в runtime-шаблоны, не коммитятся и не используются для определения лаборатории по персональным данным.

## Решения, которые не следует повторять

1. Не реализовывать новый matcher до появления expected manifest `pointId + value + unitId|null`.
2. Не использовать raw count findings как критерий качества: отдельно измеряются point precision/recall, точность value и точность unit.
3. Не объединять extraction hardening, OCR, API, matching и UI в один критерий приёмки.
4. Не строить основной алгоритм на едином эвристическом score с подобранными вручную порогами.
5. Не считать полностью одинаковый массив ячеек достаточной реконструкцией физической строки.
6. Не искать alias только внутри одной ячейки: название может быть разделено между ячейками или соседними строками.
7. Не отбрасывать всю строку только потому, что рядом с результатом присутствуют reference range, дата или другое число.
8. Не использовать hybrid fallback как доказательство улучшения structured matcher.
9. Не считать единственную разрешённую unit доказательством единицы из документа. Такое значение может использоваться только как явно отмеченное предположение для ручной проверки и не учитывается как распознанная unit.
10. Не учитывать точные копии документов как независимые примеры в quality-метриках.

## Этапы, которые можно принять как рабочие

### 1. Python extraction и hardening

Статус: `принят` как техническая основа, но не как самостоятельное улучшение matching.

Принятый результат:

- ограничение размера и числа страниц;
- корректный multipart/Form-контракт;
- несколько локальных extraction-стратегий;
- OCR fallback для страниц без пригодного текста;
- отсутствие полного извлечённого текста в межсервисном ответе;
- безопасная обработка ошибок без raw PDF payload в логах;
- локальная обработка без внешних OCR/LLM/API.

Проверка: финальный корпус обработан 14/14 без transport error; в extraction response присутствуют названия всех 242 ожидаемых DB-показателей; OCR на этом корпусе не требовался.

### 2. Изоляция и ограничения NestJS orchestration

Статус: `принят`.

Принятый результат:

- request-local catalog/findings вместо разделяемого состояния singleton;
- ограничение параллельной обработки;
- явные технические ошибки вместо успешного пустого ответа;
- компактный контракт без `pointsList`, `all_text` и raw extraction;
- отсутствие изменений медицинских нормативов и данных БД.

### 3. Инфраструктура безопасного сравнения matcher

Статус: `принят` как инфраструктура.

Принятый результат:

- pure matcher interface;
- режимы `legacy`, `shadow`, `structured`, `hybrid`;
- сохранение production default `legacy`;
- corpus/benchmark runner с агрегированным выводом без медицинских значений;
- synthetic tests для чисел, алиасов, конфликтов и колонок.

Эти инструменты пригодны для следующей реализации, но их зелёные тесты не являются приёмкой качества распознавания.

### 4. Legacy matcher как временный baseline и rollback

Статус: `принят` только как контрольная реализация.

Legacy сохраняется для baseline, shadow-сравнения и быстрого rollback. Он не считается целевым решением из-за `first candidate wins`, ограничения первой/второй ячейкой и неизвестной точности значения.

## Этапы, которые необходимо реализовать

### 1. Эталон и метрики до изменения алгоритма

Статус: `не начат`.

- создать ignored expected manifest для каждого уникального документа: `pointId`, normalized value и `unitId|null`;
- исключить точные копии из основной quality-метрики, оставив отдельную operational-метрику;
- разделить корпус по структурам документов на development и holdout subsets;
- зафиксировать baseline для point precision/recall, exact value accuracy и unit accuracy;
- не выводить названия, значения, resultId или текст PDF в отчёты и Git.

### 2. Диагностика каждого пропуска

Статус: `не начат`.

Для каждого ожидаемого, но не найденного point runner должен вернуть только безопасный код причины:

- `alias_missing`;
- `alias_split_between_cells`;
- `name_not_in_detected_column`;
- `row_split`;
- `result_column_not_detected`;
- `result_merged_with_reference`;
- `alias_collision`;
- `candidate_rejected_by_rule`;
- `conflicting_duplicate_rows`.

До этой классификации нельзя выбирать следующую эвристику или менять aliases массово.

### 3. Универсальное промежуточное представление документа

Статус: `не начат`.

В NestJS необходимо отдельно построить `DocumentTable -> LogicalRow -> CellEvidence`:

- сохранять страницу, extraction method, таблицу, индекс строки и колонки;
- объединять одинаковые представления разных extractors;
- связывать переносы только по универсальным структурным признакам;
- поддерживать alias span между соседними ячейками и строками;
- определять роли name/result/unit/reference на уровне таблицы;
- не переносить контекст только на основании одинакового количества колонок;
- не использовать шаблоны конкретных PDF или лабораторий.

Если текущего Python-контракта недостаточно для безопасной дедупликации, допускается добавить нейтральные координаты/bbox и source identifiers. Это расширение provenance, а не шаблонный parser и не изменение медицинского извлечения.

### 4. Deterministic matcher v2

Статус: `не начат`.

Алгоритм разделяется на независимые шаги:

1. найти point по alias evidence без выбора числа;
2. определить result-column или result-cell по структуре таблицы;
3. выбрать значение только из result evidence;
4. отдельно определить unit;
5. разрешить повторения и конфликты одного point;
6. вернуть finding либо конкретную причину отказа.

В основном пути не используется общий score. Приоритеты задаются детерминированными правилами и проверяются отдельными regression cases. Низкоуверенные кандидаты не заполняют форму автоматически.

### 5. Безопасный разбор value и unit

Статус: `не начат`.

- result и reference не считаются равноправными числами;
- диапазон, дата и служебное число исключаются по роли, а не отбрасывают всю строку;
- поддерживаются decimal comma/dot, scientific notation, inequality, zero и negative с сохранением признака;
- unit выбирается только при наличии evidence из документа и только среди разрешённых units point;
- предположение единственной unit может возвращаться отдельно для ручной проверки, но не считается распознанной unit.

### 6. Реальные regression fixtures без шаблонов PDF

Статус: `не начат`.

Для каждого класса ошибки создаются небольшие синтетические или обезличенные структуры extraction response. Fixture описывает общий структурный случай, а не копирует полный документ и не содержит идентификаторы, медицинский текст пациента или реальные значения.

### 7. Shadow-проверка и compatibility gate

Статус: `не начат`.

Новый matcher сначала работает в benchmark, затем в `shadow`. Переключение endpoint допускается только если:

- point precision не ниже legacy;
- point recall выше legacy на согласованную величину;
- exact value accuracy не ниже legacy;
- автоматически распознанная unit не имеет ошибок на expected manifest;
- ни одна поддерживаемая структура документа не получает необъяснимый нулевой результат;
- все оставшиеся miss/ambiguous имеют диагностическую категорию;
- concurrency, privacy и resource-limit проверки не регрессировали.

### 8. Замена экспериментального matcher

Статус: `не начат`.

После прохождения gate deterministic matcher v2 заменяет structured/hybrid в endpoint. Legacy сохраняется как rollback на один релиз. Экспериментальный scoring-код и временные unit assumptions удаляются только после подтверждённого cutover.

## Порядок следующей реализации

Обязательная последовательность:

1. expected manifest и baseline;
2. классификация 90 текущих пропусков;
3. универсальное промежуточное представление;
4. deterministic matcher v2;
5. value/unit rules;
6. regression fixtures;
7. benchmark и holdout;
8. shadow;
9. cutover либо документированный отказ от переключения.

Нельзя переходить к следующему этапу, если результат предыдущего не измерен и не зафиксирован.

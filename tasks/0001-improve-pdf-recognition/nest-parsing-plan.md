# План NestJS-парсинга: показатель и значение

Дата: 2026-10-14. Статус: этапы 1–7 реализованы, на проверке пользователя.

Итог: 236/273 правильных пар (86,4%) против baseline 144/273 (52,7%); ложных пар на текущем корпусе нет. 52 теста, сборка и read-only lint успешны. Units и Python не менялись. 37 строк остаются нераспознанными; полное распознавание и независимый внешний holdout не заявляются. Реализация и воспроизводимые результаты описаны в `implementation.md` и `nest-test-result.md`; далее сохранён утверждённый план.

## Цель и границы

Находить правильный `analysisPoint` и связанное с ним числовое значение в существующем Python response. Обрабатывать разные расположения ячеек, разделители, переносы, повторные представления и конфликты без выбора кандидата по эвристическому score.

Ограничения этого этапа:

- Python-код, extraction, OCR, состав response и HTTP-вызов Python не меняются;
- единицы не распознаются и не используются для сопоставления показателя; `unitId` и `unit` остаются `null`;
- `%`, `#`, `-CV`, `-SD` внутри имени сохраняются как признаки разновидности показателя, а не как распознавание единиц;
- runtime остаётся с одним matcher: развивать текущую реализацию по этапам, не возвращать hybrid, structured, shadow или переключатель режимов;
- контракт `findings/status/warnings/stats`, клиент, ограничения запросов и сохранение результатов не меняются;
- БД используется read-only; миграции, массовое изменение aliases и правка нормативов не входят;
- нет шаблонов лабораторий, профилей PDF, fuzzy matching, LLM или внешних сервисов;
- эталоны используются только для проверки, не как runtime-словарь или подсказка правильного значения.

Текущее поведение находится в `server/src/analysisResult/pdf-finding-matcher.ts`: alias ищется в первой ячейке, число — во второй или после alias; выбирается первый finding для point. Оркестрация — `parseFile.service.ts`, общие типы — `pdf-matching.types.ts`, benchmark — `pdf-matching-benchmark.ts`.

## Подтверждённые основания

Анализ готовых JSON: 17 документов, 24 страницы, 81 таблица, 2 161 строка. `lines` содержит 2–5 ячеек, `text` — 5–16, `coordinates` — одну ячейку на строку; 485 строк имеют пустую первую ячейку. Есть разделённые десятичные числа и заголовки, объединяющие несколько ролей.

Текущая нормализация склеивает отдельный дефис-разделитель с соседними словами. Диагностика обработки разделителей и словаря увеличила присутствие aliases со 150 до 195 эталонных записей из 273. Это оценка наличия текста, а не подтверждённый recall правильных пар. Перенос этого результата в runtime требует независимых тестов значения и precision.

Исторический baseline legacy из `nest-test-result.md`: point recall 148/265 (55,8%), value recall 144/273 (52,7%), point precision 148/152 (97,4%); четыре findings с неверным значением у ожидаемого point. Новый baseline необходимо зафиксировать тем же воспроизводимым runner, который будет оценивать изменения.

## Входы и проверка комплектности

- исходные PDF: `testData/<name>.pdf` — только инвентаризация наличия, без чтения содержимого;
- исходные эталоны: `testData/sources/<name>.json`;
- вход matcher: `testData/python-results/<name>-python.json`;
- ожидаемые поддерживаемые записи: `testData/DB-results/<name>-db.json`.

В начале прогона проверить соответствие в обе стороны и структуру JSON. Неполный набор отметить предупреждением и пропустить. Подготовленные файлы не создавать, не пересчитывать и не редактировать автоматически. Обновление Python responses, эталонов или БД требует отдельной операции.

## Этап 1. Воспроизводимая оценка и классификация baseline

Файлы: `server/scripts/pdf-matching-benchmark.ts`, новый `server/scripts/nest-parsing-corpus.ts`, `server/src/analysisResult/pdf-matching-benchmark.ts` и его тесты; правила отчёта — `testing-methodology.md`.

1. Добавить runner для сохранённых Python JSON и DB-эталонов с комплектностью, read-only каталогом и обезличенным выводом.
2. Отдельно от matcher установить соответствие эталонного имени DB point; фиксировать неоднозначность, не выбирать первый alias. Сохранить правила проверки и общий snapshot каталога для сравниваемых прогонов локально в ignored-каталоге.
3. Не сворачивать expected в `Map<pointId, row>`: разные значения и разновидности одного point не должны исчезать. Дубли одинаковых пар отдельно учитывать как повторные строки; фактический finding не должен многократно увеличивать precision.
4. Измерять point recall/precision, value recall и precision правильных пар `(pointId, value)`. Числовое совпадение строгое после разбора запятой/точки; прежний допуск `1e-9` из synthetic benchmark для этой оценки не применять.
5. Считать пропуски, лишние point, неверные значения, повторные варианты и неоднозначности; нулевой знаменатель — `н/д`. Units/triple не оцениваются в этом этапе.
6. Разделить development и holdout по структурам документов; точные копии держать в одной группе. Сохранить полный operational-отчёт, а quality-оценку дополнительно считать без точных копий.

Результат: воспроизводимый baseline и классификация причин. Проверка runner — синтетические случаи с дубликатами, лишними findings, правильным point/неверным value, пустыми эталонами и отсутствующими файлами.

## Этап 2. Нормализация названий и словарь

Файлы: `pdf-finding-matcher.ts`, его тесты; при необходимости отдельный `pdf-name-index.ts`.

1. Разделить нормализацию названий и числовых фрагментов; хранить исходный текст и соответствие позиций нормализованному тексту.
2. Исправить самостоятельный дефис-разделитель; сохранить внутренние дефисы и различающие суффиксы. Проверить `ABC - название`, `ABC-CV`, `ABC-SD`, `ABC%`, `ABC#` и кириллические сокращения.
3. Объединить explicit parsing aliases и RU/EN-названия, а не отключать переводы при непустом `translationParsing`.
4. По диагностике составить проверенный перечень недостающих общеупотребительных названий и сокращений. Если он нужен, хранить его как общий versioned словарь по стабильному имени показателя, без laboratory/template правил. Не создавать aliases автоматически из testData и не обновлять БД этим этапом.
5. Построить индекс alias → множество владельцев; неоднозначные aliases не разрешать сортировкой `parsingOrder`. Специфическое название проверять до общего, но учитывать весь найденный фрагмент имени, включая модификаторы неподдерживаемого показателя.

Результат: точный поиск имени с явными коллизиями. Проверка: нормализация, различие абсолютной/процентной формы, общее/специфическое название и неизвестный модификатор. Затем отдельный корпусный прогон поиска имён; рост присутствия aliases не объявлять ростом правильных пар.

## Этап 3. Строки и фрагменты с происхождением

Файлы: новые `pdf-row-evidence.ts`, `pdf-row-evidence.spec.ts`, внутренние типы в `pdf-matching.types.ts`.

1. Для каждой строки сохранить page, table index, extraction method, row index, исходные cells и позиции текста. Пустые ячейки сохранять.
2. Искать имя в одной ячейке и в последовательном диапазоне соседних ячеек; возвращать `NameMatch { pointId, variant, cellSpan, textSpan, source }`.
3. Перенос между строками связывать только внутри одной таблицы при явном продолжении имени, без нового имени/числового результата/заголовка. Если связь не доказана — `row_continuation_ambiguous`.
4. Не объединять таблицы и методы заранее и не превращать документ в один поисковый текст. Не склеивать произвольные слова и числа удалением всех пробелов.

Результат: найденное название связано с конкретным исходным фрагментом. Проверка: ведущие пустые ячейки, название между ячейками, перенос, новый показатель в следующей строке и повтор одного текста на разных страницах.

## Этап 4. Область результата внутри таблицы

Файлы: новый `pdf-result-region.ts` и синтетические тесты.

1. Находить заголовки name/result/reference как фрагменты между ячейками и при явном многострочном заголовке. Роль может занимать несколько соседних ячеек.
2. Применять найденную схему только к текущему участку текущей таблицы; повторный заголовок начинает новый участок. Не переносить схему по совпадению количества колонок.
3. Если заголовков нет, проверять повторяющийся порядок именованных записей и однозначные границы результата. Одной высокой доли чисел в колонке недостаточно; при нескольких подходящих областях — `result_region_ambiguous`.
4. Для одноклеточной строки использовать позицию полного фрагмента имени и границы записи. Не считать первое число после короткого кода автоматически результатом, особенно если код стоит в конце имени или строки.

Результат: для найденного показателя определена область результата либо объяснён отказ. Проверка: переставленные колонки, result/reference с одиночными числами, объединённый заголовок, отсутствие заголовка и две несовместимые схемы одинаковой ширины.

## Этап 5. Разбор и привязка числа

Файлы: новый `pdf-value-parser.ts` и тесты; подключение в единственный matcher.

1. Разбирать только установленную область результата. Сохранять исходный знак, десятичный разделитель и оператор сравнения; не брать цифры из названия, даты, reference range или служебного кода.
2. Восстанавливать разделённое десятичное число только внутри доказанной области результата. Тестировать `12` + `,5`, `12,` + `5` и отрицательный пример: два независимых числа нельзя превращать в одно.
3. Цифры, лексически являющиеся частью текстового обозначения или записи степени, не считать самостоятельным результатом. Это разметка числовых фрагментов без распознавания/сопоставления units.
4. Не подбирать число по min/max медицинских нормативов, величине похожей на ожидаемую или эталонному значению.
5. Сохранить текущую runtime-политику `0 < value < 3000` на первом срезе; ноль, отрицательные, слишком большие, качественные значения и inequalities отмечать отдельной причиной неподдерживаемости, без потери знака. Изменение этой политики требует отдельного решения.

Результат: `PairCandidate { pointId, variant, value, nameEvidence, valueEvidence, rule }` либо безопасный код отказа. Проверка: точка/запятая, знаки, разорванные числа, даты, диапазоны, несколько чисел и неподдерживаемые результаты.

## Этап 6. Повторы и конфликты

Файлы: новый `pdf-pair-resolver.ts` и его тесты.

1. Объединять одинаковые пары одного point и совместимой разновидности с сохранением всех источников, а не только идентичных массивов cells.
2. При одинаковом результате разные extraction methods служат дополнительным подтверждением; количество методов не превращается в score.
3. Если валидные кандидаты дают разные значения — `conflicting_values`; не выбирать первый, большинство голосов или максимальный score.
4. Различающиеся `variant` не схлопывать. Если API допускает только один finding на point и невозможно однозначно выбрать разновидность — явная неоднозначность и отсутствие выбранного значения.
5. Невалидное или недоказанное представление не должно вытеснять доказанную пару только потому, что обработано раньше.

Результат: подтверждённые пары и объяснимые конфликты. Проверка: одинаковые записи разных методов, разбиение cells, конфликт значений, разные разновидности одного point и перестановка порядка таблиц/методов.

## Этап 7. Интеграция и приёмка

Файлы: `pdf-finding-matcher.ts`, `parseFile.service.ts`, сервисные tests, CLI и отчёт `nest-test-result.md`.

1. После проверки отдельных этапов подключить их как единственный путь matcher. Не добавлять legacy fallback, shadow logging или mode flags; исходный baseline доступен через Git и исторический отчёт.
2. Сохранить request-local данные и лимит concurrency. `unitId/unit` возвращать `null`; confidence не выводить из суммы эвристических баллов и не трактовать как вероятность правильности. На этом срезе оставить техническое значение `0.5`.
3. Отказы и конфликты отражать обезличенными codes/counts, без исходного текста, значений и filenames в application logs. `partial` для неполного/неоднозначного результата, `unsupported` при отсутствии поддержанных findings; `complete` не объявлять по одному лишь отсутствию исключений.
4. Добавить каждый прогон отдельным датированным блоком в `nest-test-result.md`; сохранить baseline и историю.
5. Выполнить backend tests/build/read-only ESLint, проверку формата ответа, параллельных запросов, ошибок и отсутствия чувствительных payload в логах. Python/client тесты не расширять без изменения этих слоёв.

Критерии приёмки:

- синтетические позитивные и негативные тесты всех этапов проходят;
- на фиксированном корпусе point recall и value recall не ниже baseline; количество правильных пар выросло, pair precision не снизился;
- отдельно проверить отсутствие ухудшения по документам: любое уменьшение correct pairs классифицировать, а не скрывать общим итогом;
- на holdout нет увеличения ложных пар; копии документов не считаются независимыми примерами;
- выбор числа имеет name/value evidence, не зависит от порядка обхода и не использует эталон;
- спорные пары отклоняются с объяснением; изменения справочника или эталонов не маскируют ошибки реализации;
- `git diff --check` пройден, чувствительные файлы и generated artifacts не входят в diff.

Безопасные численные цели сверх baseline определить после первого воспроизводимого прогона; 100% не обещать для данных, где JSON потерял связь между названием и результатом.

## Риски, поставка и rollback

- В существующем JSON нет bbox. Некоторые переносы и конкурирующие числа могут остаться неразрешимыми: фиксировать ограничения, Python на этом этапе не менять.
- Полнота aliases ограничивает recall; новый alias может создать коллизию. Каждый вариант проверять с негативным случаем, не изменять БД массово.
- Разные исходные разновидности могут соответствовать одному DB point. Сохранять variant и отказываться от неоднозначного выбора; этап не расширяет контракт результата.
- Улучшение числового парсинга само по себе не разрешает новые категории результатов. Поддержка нуля, отрицательных и inequalities остаётся отдельным решением.
- Основные внутренние этапы реализовывать небольшими проверяемыми изменениями. Код приложения пока не менялся в рамках этого планирования; база сравнения — текущий legacy.
- Миграция не нужна. Поставка — обычное обновление server после приёмки; Python image и client не требуют изменения. Rollback — восстановить принятую legacy-реализацию из Git и server image, сохранив безопасный контракт и ограничения запросов.
- До фиксации этого плана создана и проверена локальная резервная копия БД; данные не менялись.

### Результат проверки

Compatibility gate не пройден. Агрегированное proxy-покрытие structured matcher составляет 26,6%, что ниже legacy baseline 51,1% и предыдущего эксперимента 30,9%. Без expected manifest нельзя вычислить precision, recall, exact value accuracy и unit accuracy, однако текущего падения raw coverage и одного подозрительного numeric finding достаточно, чтобы не переключать runtime default.

`PDF_MATCHER_MODE` должен оставаться `legacy` либо `shadow`. Режим `structured` допустим только для дальнейшего benchmark/debug до исправления подтверждённых misses и прохождения expected gate.

### Анализ плюсов исходного алгоритма

Исходный код обеспечивал высокую полноту за счёт нескольких простых и устойчивых правил:

- использовал уже подготовленный предметный словарь aliases, включая короткие медицинские аббревиатуры;
- искал alias в первой ячейке, то есть в естественной позиции названия показателя;
- брал значение из соседней ячейки, что хорошо соответствует большинству простых лабораторных таблиц;
- детерминированно выбирал первый допустимый результат и не терял весь point из-за расхождения дополнительных extractors;
- возвращал не более одного finding на point.

Hybrid matcher сохраняет эти свойства как compatibility fallback, но сначала использует более строгий structured-кандидат. Structured finding имеет приоритет; legacy добавляет только отсутствующий point и помечает его `legacy_compatibility_fallback`. Это упрощает resolver и не заставляет слабый legacy-кандидат конкурировать со структурно подтверждённым.

### Выводы

1. Предметное допущение о коротких английских аббревиатурах длиной до трёх символов подтвердилось на proxy-метрике: structured coverage выросло с 62 до 71 findings, или на 14,5% относительно предыдущего structured-прогона. Collision и tolerant aliases по-прежнему требуют строгого контекста.
2. Hybrid восстановил 51 finding через legacy fallback и получил 122 findings — на 3 больше baseline. Это лучший raw coverage из четырёх проверенных вариантов, но не доказательство лучшей точности.
3. 51 из 122 findings (41,8%) зависят от legacy fallback. Поэтому hybrid пока существенно опирается на исходный алгоритм, а не заменяет его.
4. Допущение единственной разрешённой unit сократило findings без unit с 47 до 8. Оно применилось к 90 из 122 findings (73,8%) и всегда отмечено `unit_assumed_from_single_allowed`; при нескольких разрешённых units выбор не выполняется.
5. 98 из 122 findings (80,3%) имеют предупреждения, поэтому все восемь непустых документов получили `partial`. Основные причины — fallback и assumed unit, а не новый конфликт значений.
6. Три findings сверх legacy требуют проверки: они могут быть полезными структурными находками либо false positive. Finding с одновременными `negative_value_requires_review` и `large_value_requires_review` также остаётся подозрительным.
7. Для `noname_file_06` и `noname_file_07` ни один вариант не нашёл point. Это указывает на отдельный miss словаря/profile/layout, который объединение алгоритмов не исправляет.

### Решение по результатам

Hybrid — предпочтительный кандидат для следующего expected benchmark: он возвращает полноту исходного алгоритма, добавляет структурные находки и резко сокращает неопределённость units. Однако переключать default на `hybrid` пока нельзя, потому что raw count не измеряет precision, exact value accuracy и unit accuracy.

До переключения необходимо вручную сверить локальный ignored expected manifest как минимум для:

- 51 fallback finding;
- 3 findings сверх legacy;
- 90 assumed units, особенно на границах разных разрешённых units;
- negative/large finding и четырёх ambiguous groups;
- двух полностью нераспознанных документов.

Runtime default остаётся `legacy`; для накопления безопасных агрегатов допустим `shadow`, а `hybrid` включается явно через `PDF_MATCHER_MODE=hybrid` только для проверки. После expected gate критерии переключения прежние: point precision/recall и exact value accuracy не ниже baseline, подтверждённая unit accuracy и отсутствие регрессий privacy/concurrency.

## 7. Сколько параметров должно распознаваться с текущим справочником БД

### Методика анализа

Выполнено read-only сопоставление тех же 10 PDF с текущим справочником PostgreSQL:

- 67 заведённых `analysisPoint`;
- primary aliases из `translationParsing`;
- точные RU/EN-переводы как дополнительный слой;
- каноническая нормализация регистра, Unicode, пробелов и пунктуации;
- уникальность считается по паре «документ + point», поэтому один point в разных PDF учитывается несколько раз;
- алиас, относящийся к нескольким point, не считается однозначным и вынесен в отдельный диапазон.

Tolerant/confusable совпадения не использовались как доказательство наличия point в БД: они полезны для OCR, но могут создавать дополнительные коллизии. Имена файлов, параметры, значения, aliases и извлечённые строки в отчёт не выводились. Порядок `noname_file_04`/`noname_file_05` приведён к прежнему историческому соответствию.

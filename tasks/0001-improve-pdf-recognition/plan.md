# Задача 0001: повышение полноты и корректности распознавания PDF

## Цель и границы

Цель — сделать обработку лабораторных PDF предсказуемой: извлекать числовые показатели из текстовых и сканированных документов, не смешивать параллельные запросы, не подменять единицы и явно отражать в API частичное либо неуспешное распознавание.

P0 hardening и generic OCR находятся на проверке. Экспериментальный conflict-aware NestJS matcher оказался хуже baseline по raw findings и был откатан до legacy compatibility-логики при сохранении нового контракта. Новый структурный matching-срез из `matching-solution.md` реализован за feature flag и находится на проверке; legacy остаётся режимом по умолчанию до прохождения compatibility gate на локальном expected manifest. Схема и данные БД не изменялись; локальный корпус `testData` обработан только агрегатными проверками.

В границы будущей реализации входят:

- загрузка и валидация PDF;
- извлечение текста/таблиц в Python-сервисе;
- сопоставление строк со справочником показателей в NestJS;
- разбор значения и единицы;
- контракт ответа и невизуальная адаптация client data layer;
- приватность, ограничения ресурсов, ошибки и обезличенная наблюдаемость;
- синтетический и обезличенный regression-корпус.

Не входят:

- медицинская верификация нормативов и интерпретаций;
- автоматическое сохранение результата без подтверждения пользователя;
- любые обращения runtime-процесса к внешним OCR/LLM/API, model hub, CDN или другим сетевым ресурсам;
- массовая правка словаря `translationParsing`;
- изменение production-данных;
- визуальные изменения client: показ `complete/partial/unsupported`, confidence/warnings, новые review-блоки, подтверждение распознавания и изменение существующего UI выбора единиц; это выносится в отдельную задачу.

## Наблюдаемое и ожидаемое поведение

Наблюдаемое поведение: часть PDF даёт неполный набор показателей, пустой набор либо ошибочные совпадения. Ошибка Python-сервиса превращается в успешный ответ NestJS с пустым `findingPoints`, поэтому клиент не отличает «ничего не найдено» от технического сбоя. Сканированные страницы не распознаются.

Ожидаемое поведение:

- текстовый PDF обрабатывается несколькими безопасными стратегиями извлечения;
- OCR запускается только для страниц без пригодного текстового слоя;
- найденные имя, значение и единица связаны с одной строкой/областью и имеют оценку уверенности;
- неоднозначные и конфликтующие кандидаты не выбираются молча;
- API однозначно возвращает `complete`, `partial`, `unsupported` или явную ошибку; в текущей задаче visual UI для этих состояний не добавляется;
- полный текст и бинарное содержимое PDF не возвращаются, не сохраняются и не попадают в логи;
- лимиты страниц, размера, времени, памяти и параллелизма реально применяются;
- повторные и параллельные запросы изолированы.

## Текущий поток

1. `client/src/pages/analysis/Dropfile.tsx` принимает один PDF до 10 MiB.
2. `client/src/entities/analysisResult/model/extraReducers.ts` отправляет его в `POST /result/fromFile`.
3. `server/src/analysisResult/analysisResult.controller.ts` применяет `MaxFileSizeValidator` и `FileTypeValidator`; установленная версия NestJS проверяет magic number.
4. `server/src/analysisResult/parseFile.service.ts` загружает 67 показателей и их ручные алиасы из БД, затем отправляет буфер в Python.
5. `server/src/pdf-parser/pdf-parser.service.ts` формирует multipart-запрос к `/extract-tables`, передавая `pages=1-5` и line-based настройки.
6. `python-microservice/app.py` использует `pdfplumber`: `extract_tables()`, затем `find_tables()`, а при полном отсутствии таблиц — группировку символов по координате Y.
7. NestJS ищет алиас только в `row[0]`, берёт первое число из `row[1]` либо из остатка единственной ячейки и принимает только `0 < value < 3000`.
8. Для каждого показателя сохраняется первый кандидат, единица всегда возвращается как `0`.
9. Client заменяет введённый набор найденными показателями, а затем автоматически выбирает первую разрешённую единицу.

## Подтверждённые проблемы

### P0 — корректность и приватность

1. **`pages` и `table_settings` фактически игнорируются.** В FastAPI они объявлены как обычные параметры, то есть читаются из query, а NestJS отправляет их multipart-полями. Для сочетания файла и полей FastAPI требует `Form(...)`. Синтетический запрос с заведомо недопустимой настройкой вернул HTTP 200, подтвердив, что поле не разобрано.
2. **Обрабатываются все страницы, а не 1–5.** Это повышает время/память и передаёт в NestJS текст страниц, которые предполагалось не обрабатывать. Если после исправления `Form(...)` оставить текущий разбор диапазона, запрос `1-5` к одностраничному PDF падает с HTTP 500 из-за выхода за границы массива.
3. **Состояние между запросами общее.** `ParseFileService` — singleton, а `findingPoints` и `pointsList` хранятся в его полях. Перекрывающиеся загрузки могут очистить/изменить состояние друг друга, смешать результаты и создать риск межпользовательской утечки.
4. **Техническая ошибка маскируется как успех.** `PdfParserService` ловит исключение, печатает объект ошибки и возвращает `null`; верхний слой всё равно отвечает `{ message: "success", findingPoints: [] }`.
5. **В ответе Python всегда присутствует `all_text`.** Это полный извлечённый медицинский текст, хотя matching его не использует. `fallback_text` также не используется. Полный текст без необходимости пересылается между сервисами.
6. **Логируется полный объект Axios-ошибки.** В нём может находиться конфигурация multipart-запроса и буфер PDF. Ошибки Python включают внутренний текст исключения в HTTP 500.
7. **Python-сервис опубликован на host-порту `8000` даже в production compose.** Прямой запрос обходит NestJS-лимит и magic-number проверку; в Python есть только чувствительная к регистру проверка имени `.pdf`, нет лимита размера и endpoint не защищён.

### P0 — неполное или ошибочное извлечение

1. `pdfplumber` не выполняет OCR. В image-only PDF нет `chars`, поэтому такой документ возвращает пустой результат. Tesseract установлен в image, но код его не вызывает; список установленных trained languages пуст.
2. Line-based извлечение плохо подходит таблицам без рамок. Стратегия `text` не используется, а координатный fallback запускается только когда на странице не нашлось вообще ни одной таблицы. Частично распознанная таблица блокирует разбор остального текста страницы.
3. `extract_tables(lines)` и `find_tables()` с настройками по умолчанию по существу повторяют одну line-based стратегию и могут возвращать дубли, а не независимые варианты.
4. Matching смотрит на имя только в первой ячейке, значение — только во второй. Он пропускает переставленные колонки, пустую первую ячейку после переноса строки, объединённые ячейки и значение в третьей/четвёртой колонке.
5. Координатный fallback сортирует `y0` по возрастанию, то есть возвращает строки снизу вверх. Это подтверждено визуально проверенным одностраничным синтетическим PDF.
6. Для координатного результата отсутствует `cols`, хотя TypeScript-контракт ожидает число.
7. Возвращается первый кандидат показателя. При повторении показателя, нескольких методах извлечения или конфликтующих значениях нет сравнения источников; из-за обратного порядка координат это может быть нижнее, а не верхнее значение на странице.

### P0/P1 — matching, числа и единицы

1. Фразы сравниваются простым `includes`, одиночные алиасы — точным сравнением после ограниченного split. Нет Unicode NFKC, нормализации NBSP, дефисов, пунктуации, похожих кириллических/латинских символов и OCR-ошибок.
2. Приоритет строится по длине всей строки `translationParsing`, а не конкретного совпавшего алиаса. Короткий алиас у показателя с длинным списком может затенить специфичный алиас другого показателя.
3. Агрегатный аудит локальной БД: 67 показателей, 196 алиасов, 66 алиасов с пробелами, 15 алиасов длиной не более двух символов, 3 значения алиаса назначены более чем одному показателю; применяется только 4 уровня `parsingOrder`. У всех 67 показателей есть custom-алиасы, поэтому fallback на RU/EN-название сейчас не используется.
4. Синтетический немедицинский отчёт с двумя нейтральными строками дал один найденный показатель. Это демонстрирует отсутствие проверки контекста и риск false positive для коротких/общих алиасов.
5. Regex не поддерживает научную запись, числа с разделителями тысяч, ведущую десятичную точку и качественные/неравные значения. Например, `1.2e9` превращается в `1.2`, а `1 234,5` — в `1`.
6. Глобальное условие `0 < value < 3000` не имеет общей медицинской семантики: ноль и значения от 3000 отбрасываются, независимо от показателя и единицы. Убирать или менять этот порог можно только вместе с предметной проверкой.
7. Python/NestJS единицу не извлекают. В client первая разрешённая единица назначается автоматически, даже если у показателя их несколько. При ручной смене единицы `parseInt(pointValue)` обрезает дробную часть.

### P1 — UX, контракт и сопровождение

1. Client не показывает число пропущенных/сомнительных строк, тип документа, confidence, источник и причину частичного результата.
2. Reject от `react-dropzone` (например, >10 MiB) не отображается явно.
3. NestJS возвращает неиспользуемый `pointsList` со всем словарём. На синтетической загрузке ответ составил около 50 KiB вместо компактного списка кандидатов.
4. Нет unit/integration-тестов PDF-потока и синтетического regression-корпуса.
5. Python-зависимости существенно устарели относительно текущих веток (`pdfplumber 0.10.4`, `fastapi 0.104.1`, `python-multipart 0.0.6`). Обновление нужно делать отдельным проверяемым этапом, без безусловного массового upgrade.

## Варианты решения

### Вариант A — стабилизировать текущий text-PDF pipeline

Состав: исправить контракт FastAPI, сделать состояние request-local, убрать полный текст, добавить реальные лимиты и типизированные ошибки; извлекать строки стратегиями `lines`, `text` и layout text; нормализовать строки, разбирать колонки/единицы и оценивать кандидатов.

Плюсы: минимальный новый стек, быстрый эффект для machine-generated PDF, проще тестировать. Минусы: image-only/плохие OCR PDF останутся неподдержанными.

Вердикт: обязательный первый этап при любом варианте.

### Вариант B — гибридный локальный OCR

Состав: сначала классифицировать каждую страницу по наличию пригодного текстового слоя; только image-only/непригодные страницы локально rasterize + OCR (`rus`/`eng`), затем прогнать через общий нормализатор и matcher. Практичный кандидат — OCRmyPDF/Tesseract с page limits, deskew/rotate и timeout; для mixed PDF использовать skip/redo режим по результатам эксперимента.

Плюсы: закрывает сканы и смешанные документы, PDF не покидает инфраструктуру. Минусы: больше CPU/RAM/temp disk, нужны traineddata, очередь/изоляция и более строгие лимиты; OCR таблиц всё равно требует layout-логики.

Вердикт: рекомендуемый второй этап после A.

### Вариант C — профили известных лабораторий

Состав: определять шаблон по устойчивым признакам и применять проверенные правила колонок/областей, сохраняя generic pipeline как fallback.

Плюсы: высокая точность на популярных стабильных форматах, объяснимость. Минусы: постоянное сопровождение шаблонов, хрупкость при редизайне, не покрывает неизвестные лаборатории.

Вердикт: полезное дополнение после появления anonymized benchmark; не должно быть единственным движком.

### Вариант D — локальная layout-aware ML-модель

Состав: только заранее подготовленная и включённая в локальный image layout-aware модель без runtime-загрузок весов, словарей или кода.

Плюсы: потенциально лучше на разнообразных макетах и OCR. Минусы: ресурсоёмкость, latency, сложная воспроизводимость, необходимость размеченного корпуса и model drift.

Вердикт: не использовать как базовое решение задачи 0001. Рассматривать отдельным ADR/пилотом только после измерения A+B+C. Внешний Document AI/LLM исключён из вариантов реализации.

## Рекомендуемое решение

Выбранное для предложения направление: **A → B → при необходимости C**, с единым детерминированным candidate pipeline. Весь runtime работает offline и использует только заранее подготовленные локальные ресурсы. Реализация начнётся только после подтверждения остальных приоритетов и формирования обезличенного benchmark.

Целевой поток:

1. Validate PDF magic, размер, шифрование, фактическое число страниц и сложность до тяжёлого разбора.
2. Ограничить обработку страниц пересечением запрошенного диапазона и `1..total_pages`; недопустимые параметры возвращать как 4xx.
3. Для каждой страницы определить `digital-text`, `mixed` или `image-only` без сохранения текста.
4. Для digital-text параллельно получить line-table, text-table и layout rows; fallback должен дополнять, а не взаимоисключать результаты.
5. Для image-only выполнить локальный OCR с `rus+eng`, поворотом/deskew и жёстким timeout.
6. Преобразовать всё в единый внутренний `CandidateRow`: page, bbox, cells, method, без передачи полного документа наружу.
7. Нормализовать Unicode/пробелы/пунктуацию; найти возможные колонки имени, значения, единицы и референса.
8. Разобрать число без потери исходной семантики (`decimal`, scientific notation, inequality); медицински сомнительное не отбрасывать молча, а помечать warning.
9. В compatibility-срезе сохранить legacy matching: alias ищется в первой ячейке, число — в следующей либо после alias в одноклеточной строке, выбирается первый допустимый кандидат. Новый контракт должен сообщать результат как `findings/status/warnings/stats`; улучшенный conflict-aware matcher остаётся отдельным следующим этапом.
10. Deduplicate совпадающие кандидаты разных extractors, но сохранить конфликтующие варианты для проверки.
11. Ответить компактным контрактом: `status`, `findings[]`, `warnings[]`, безопасная статистика страниц. Не возвращать `all_text`, `rawResponse` и весь `pointsList`.
12. Client data layer принимает новый контракт и заполняет существующую форму из `findings`; визуальное представление status/confidence/warnings и новый review flow не меняются в этой задаче.

## Этапы реализации

### Корректировки по результатам проверки `testData`

Проверка от 2026-08-29 зафиксировала 72 findings на 233 структурно посчитанные строки показателей (30,9%), 7 ответов `partial`, 3 `unsupported` и отсутствие `complete`. До приёмки задачи обязательны следующие корректировки:

1. **Локальный expected manifest и benchmark runner.** Для каждого обезличенного файла локально зафиксировать ожидаемые point, value и unit; чувствительные значения не коммитить. Runner должен выводить только агрегаты precision/recall, unit accuracy, статусы и категории расхождений.
2. **Разделение result/reference.** Определять колонки результата, единицы и референсного диапазона по заголовку; числа из reference, дат и примечаний исключать из кандидатов значения.
3. **Контекст продолжения таблицы.** Переносить роли колонок на таблицы-продолжения и следующие страницы того же макета, пока не встретится новый явный заголовок.
4. **Дедупликация до разрешения конфликтов.** Сначала объединять представления одной физической строки от `lines`, `text`, `coordinates` и OCR по page/bbox/нормализованному содержимому; затем сравнивать значения. Структурную строку с найденной result-column приоритизировать над плоской coordinate-строкой.
5. **Слоистый alias index.** Использовать `translationParsing` как primary-слой, RU/EN-названия — только как exact fallback. Короткий canonical English alias длиной до трёх символов считать сильным сигналом в первой/name ячейке; collision и tolerant/confusable aliases оставлять только для строгого контекста. Не выполнять плоское объединение: на текущем корпусе оно не добавило point mentions и увеличивает пары вложенности с 17 до 229. Неоднозначный alias не выбирать автоматически.
6. **Контекстные warnings.** Добавлять `alias_collisions_detected` только если неоднозначный alias реально встретился в документе; глобальные коллизии словаря не должны переводить каждый ответ в `partial`.
7. **Unit matching.** Добавить проверяемые локальные aliases вариантов записи единиц. В hybrid-режиме назначать единственную разрешённую для point unit с явным warning; при нескольких разрешённых units отсутствие или неоднозначность оставлять для ручного выбора.
8. **Regression coverage.** Добавить синтетические тесты для отсутствующего alias, нескольких чисел в строке, продолжения таблицы без заголовка, конфликта extractors и полного отбрасывания кандидатов.
9. **Dev-конфигурация parser.** Устранить расхождение между документацией и `docker-compose.dev.yaml` по публикации `8000:8000`: выбрать и явно зафиксировать безопасный режим локальной отладки.

После реализации повторить прогон того же корпуса. Структурное отношение `findings/rows` использовать только как предварительную метрику; критерием корректности являются precision/recall и unit accuracy по expected manifest.

Подробный read-only аудит текущего словаря и варианты A–D зафиксированы в `alias-analysis.md`.

### Этап 0 — benchmark и regression tests

- Создать полностью синтетические fixtures: таблица с линиями, без линий, переносы, несколько таблиц, разные порядки колонок, multi-page, rotated scan, image-only, mixed, corrupt, encrypted, oversized/complex.
- Пользователь отдельно подтверждает небольшой обезличенный набор реальных макетов. В Git хранить только явно обезличенные fixtures; иначе использовать локальный ignored corpus и сохранять лишь агрегатные метрики.
- Зафиксировать expected findings и метрики precision/recall по строкам, unit accuracy, document success/partial rate, p95 latency и peak memory.

### Этап 1 — P0 hardening и честный контракт

Затрагиваемые файлы: `python-microservice/app.py`, `requirements.txt`, Dockerfile/compose, `server/src/pdf-parser/*`, `server/src/analysisResult/parseFile.service.ts`, controller и тесты.

- `Form(...)`, строгая модель options, clamp страниц;
- request-local состояние;
- исключение `all_text`/деталей ошибок/буферов из ответа и логов;
- typed error/partial response вместо silent success;
- внутренний-only production port Python-сервиса;
- лимиты размера, страниц, времени, памяти/worker concurrency;
- обработка всех candidate rows и устранение дублирующих extractor-результатов.

### Этап 2 — matching, unit и client contract adapter

Затрагиваемые файлы: matcher/DTO в server, analysisPoint dictionary/admin validation и Redux types/slice. `Dropfile`, `AnalysisPage` и selected-item UI не изменяются.

- сохранить legacy-поиск по первой ячейке и первой допустимой числовой величине, адаптировав его вход к новому Python-ответу;
- возвращать `findings/status/warnings/stats`, не возвращая `pointsList` и `all_text`;
- unit в compatibility-срезе не угадывать и возвращать как `null`; conflict-aware matching, aliases и структурный разбор остаются отдельным этапом;
- невизуальный adapter нового `findings/status/warnings/stats` контракта к существующему Redux state;
- visual review, запрет автоматического выбора первой единицы и исправление клиентского `parseInt` остаются отдельной frontend-задачей.

### Этап 3 — условный локальный OCR

- заранее включить в image и зафиксировать по версиям/checksum `rus`/`eng` traineddata; runtime-загрузка запрещена;
- рассмотреть Debian slim вместо Alpine, если это уменьшит сложность OCRmyPDF/qpdf/Ghostscript dependencies;
- OCR только нужных страниц;
- отдельный process/worker с timeout и resource limits, чтобы CPU-задача не блокировала `/health`;
- не сохранять входной PDF, OCR-PDF, изображения и sidecar text после запроса.

### Этап 4 — профили и эксплуатационные метрики

- добавить профили только для макетов, где generic pipeline не достигает целевой recall;
- логировать только request id, тип страницы, extractor, длительность, количества candidates/findings/warnings и код ошибки;
- не логировать имя файла, текст, значения, единицы, point name/id, resultId или buffer.

## API и схема данных

Предлагаемый новый ответ `POST /result/fromFile`:

```text
status: complete | partial | unsupported
findings[]:
  pointId
  value
  unitId | null
  confidence
  page
  warnings[]
warnings[]
stats: pagesTotal, pagesProcessed, pagesOcr, candidates, matched
```

`stats` не должен содержать медицинских значений. На первом этапе схему БД можно не менять: собрать нормализованный индекс из `translationParsing` в памяти и валидировать коллизии. Нормализованная таблица aliases с отдельными priority/language/lab-profile — возможный следующий этап, требующий отдельной миграции, backup, dry-run и подтверждения пользователя.

## Приватность, безопасность и медицинская интерпретация

- PDF и извлечённый текст обрабатываются только локально и только в памяти/защищённом temp с гарантированным удалением.
- Runtime-процесс не выполняет исходящие обращения во внешние сети. OCR engine, модели, traineddata, словари, профили лабораторий и остальные ресурсы заранее упаковываются в versioned image либо подключаются из контролируемого локального read-only volume.
- Python-сервис следует вынести в отдельную internal Docker network с NestJS без маршрута во внешнюю сеть; наличие локальной связи server → parser не должно давать parser internet egress.
- Runtime не устанавливает пакеты и не скачивает модели. Подготовка и обновление image выполняются отдельным контролируемым процессом поставки с lock-файлами/checksum и regression benchmark.
- Нельзя возвращать/логировать `all_text`, raw rows, filename и traceback с содержимым.
- Python endpoint не должен быть доступен извне production-сети.
- Public NestJS endpoint нуждается в rate/concurrency limiting.
- OCR/парсинг выполняется в ограниченном worker-процессе; HTTP timeout сам по себе не прекращает CPU-работу.
- Значение, unit и point должны подтверждаться пользователем. Confidence — техническая оценка, не медицинская достоверность.
- Универсальный порог 3000 нельзя заменять другим числом без проверки по point+unit. Лучше вернуть кандидата с warning и применить проверяемые per-point правила после предметного решения.
- Результат остаётся справочным и не является диагнозом.

## Миграция и rollback

Этапы 0–3 не требуют изменения схемы БД. Deployment можно делать feature flag по новому parser contract и откатывать возвратом прежнего container image/server-client release. Нельзя откатываться к возврату полного `all_text` или небезопасному публичному Python endpoint.

Если будет выбрана отдельная aliases-таблица, для неё нужен самостоятельный migration plan: read-only collision report, backup, backfill на копии, unique/index constraints после разрешения конфликтов, повторный запуск и down/rollback.

## Критерии приёмки

- Данные из всех файлов в локальной папке `testData/` успешно и корректно распознаются; проверка выполняется локально без вывода содержимого PDF, извлечённых медицинских данных и индивидуальных результатов в логи, документы задачи или Git.
- Все synthetic fixtures имеют ожидаемый статус и findings; corrupt/encrypted/oversized дают контролируемые 4xx/422, timeout — контролируемую 5xx/503 без traceback.
- Точные значения, decimal comma/dot, scientific notation, zero, negative, inequality и большие значения либо корректно разобраны, либо явно помечены; ничего не искажается молча.
- Backend определяет unit только при однозначности; визуальное поведение выбора unit в client сохраняется без изменений в рамках этой задачи.
- Line-less, multi-column, wrapped rows, image-only и mixed PDF покрыты тестами.
- Две параллельные загрузки и повтор одного файла не смешивают findings.
- Ни response, ни application/container logs не содержат PDF bytes, filename, полного текста, raw rows или индивидуальных значений.
- Python не опубликован наружу production compose; реальные limits применяются на обоих слоях.
- Автоматическая проверка подтверждает отсутствие внешнего network egress у parser-контейнера; работа text/OCR pipeline не зависит от доступности интернета, DNS или стороннего API.
- Для согласованного обезличенного benchmark определены и достигнуты целевые precision/recall и p95; числа задаются после формирования корпуса, а не угадываются заранее.
- Backend/client build, Python compile/health, unit/integration/e2e smoke, `git diff --check` проходят.

## Риски и открытые решения

- Нужен подтверждённый обезличенный benchmark, иначе нельзя честно измерить улучшение полноты по реальным макетам.
- Нужно согласовать максимальное число обрабатываемых страниц: текущая заявка — 1–5, фактическое поведение — все страницы.
- Нужно решить, поддерживаются ли значения с неравенством/качественные результаты и как показывать их в текущей числовой модели.
- Нужна предметная политика допустимости числа по point+unit вместо общего порога 3000.
- Visual client пока не показывает status/confidence/warnings и сохраняет прежнее автоматическое назначение первой unit; устранение этого риска вынесено из `0001` по решению пользователя от 2026-08-29.
- OCR увеличит ресурсы и latency; перед включением нужны нагрузочные лимиты и метрики.
- Dependency upgrade выполнять изолированно с benchmark, поскольку изменение `pdfminer.six/pdfplumber` может менять геометрию и строки.

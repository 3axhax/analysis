# GEO И SEO оптимизация

Дата постановки: 2026-10-19. Статус: планирование, реализация не начата.

## Цель

Улучшить доступность и понятность публичных страниц proanalize.ru для поисковых систем и генеративного поиска (GEO), сохранив справочный характер сервиса и исключив медицинские результаты из индексации. Повысить доверие за счёт достоверных сведений о проекте, источниках и ограничениях алгоритма.

Основание: [аудит production](audit.md). Постановка задачи не разрешает автоматически публикацию изменений или создание медицинских материалов без предметной проверки.

## Наблюдаемое и ожидаемое поведение

Сейчас robots.txt и sitemap.xml отдают HTML главной, неизвестные адреса — 200, исходный HTML не содержит основного контента, canonical проверенных страниц указывает на главную. Служебные маршруты получают общий index, follow. «О проекте» и «Контакты» содержат шаблонный контент. JSON-LD обещает диагностику.

Ожидается: валидные служебные файлы, корректные статусы и canonical, доступный в исходном HTML публичный контент, явный noindex для результатов и служебных страниц, достоверное описание сервиса и методологии. Результаты и API не включаются в sitemap.

## Решение и этапы

### 1. Техническая индексация — высокий приоритет

- Определить матрицу URL: индексируемые, дубли, служебные, результаты, отсутствующие.
- Создать robots.txt (text/plain) и XML sitemap только с каноническими публичными страницами; указать sitemap в robots.
- Для /result/*, admin и других служебных страниц задать серверный X-Robots-Tag: noindex. Не использовать один Disallow как замену noindex: робот должен прочитать директиву. Не считать это контролем доступа.
- Возвращать 404 для неизвестных URL, сохранив прямое открытие существующих SPA-маршрутов, API и статических ресурсов.
- Canonical самостоятельных страниц должен соответствовать их URL. Для /analysis выбрать 301 на /, если функции остаются одинаковыми. www перенаправлять на основной HTTPS-хост после проверки TLS и конфигурации.
- Исправить lang, согласовать title/description исходного HTML и DOM, доступность favicon/logo, JSON-LD. Удалить обещание «точной диагностики».

### 2. Рендеринг публичного контента — высокий приоритет

Выбрать prerender/SSG либо SSR после небольшого технического исследования. Для ограниченного набора публичных страниц сначала оценить prerender, без обязательного переноса всего приложения на другой framework. Отдавать заголовки, смысловой текст и внутренние ссылки без выполнения JS. Форму оставить интерактивной; персональные результаты никогда не включать в статическую сборку, общий cache или HTML публичных страниц. Не применять отдельный контент для роботов.

### 3. Доверие и методология — высокий приоритет

- Заменить шаблоны о проекте и контактах на согласованные достоверные сведения; сделать эти страницы доступными из навигации.
- Описать действительный алгоритм сравнения, источники референсов, age/gender/unit, отсутствие/конфликт норматива, ограничения PDF и проверку распознавания пользователем.
- Указать настоящих авторов/рецензентов и их квалификацию только при наличии подтверждения, даты проверки и источники. Если рецензентов нет, не создавать вымышленные атрибуты доверия.
- Согласовать видимые обещания, JSON-LD и политику работы с данными. Подчеркнуть справочное назначение и отсутствие диагноза.

### 4. Тематические страницы и GEO — после предметной проверки

Подготовить содержательные страницы направлений (например, ОАК, ферритин, щитовидная железа) и показателей. Структура: краткий ответ, что измеряется, единицы, причины различий референсов, ограничения выводов по одному значению, источники и дата проверки, переход к форме. Добавить практические ответы о PDF и интерпретации. Не публиковать массово шаблонные статьи, непроверенные нормативы или отдельные страницы под каждую формулировку запроса.

Structured data должна соответствовать видимому содержанию; типы и свойства валидировать. Специальные GEO-файлы/разметка не являются условием попадания в ИИ-ответы; llms.txt не считать заменой SEO и не включать в обязательный первый этап.

### 5. Измерение и поставка

С согласованным доступом проверить Google Search Console и Яндекс Вебмастер, отправить sitemap. Снять baseline индексации, запросов/переходов и Core Web Vitals; отдельно отмечать измеряемые переходы из ИИ. Не собирать значения анализов, PDF, tokens, capability IDs/URL и содержимое форм в аналитике. Не давать гарантий позиций или цитируемости.

## Приватность, API и БД

Начальные этапы не требуют изменений схемы, нормативов, сохранённых результатов или API-контрактов. Не индексировать и не публиковать результаты; для тестов использовать только синтетические данные. Медицинский контент согласовывать предметно. Не использовать production-БД/реальные PDF для генерации страниц.

Если выбранный способ хранения контента потребует БД, сначала дополнить план: миграция/down, read-only аудит, проверенный backup, проверка на копии и отдельное подтверждение. Текущая задача таких изменений не разрешает.

## Проверка и критерии приёмки

- robots.txt: 200, text/plain, корректный синтаксис; sitemap: 200, валидный XML, только предназначенные для индексации canonical URL.
- Матрица ответов проверена HTTP GET и после JS: публичные страницы 200, неизвестные 404, выбранные дубли 301 без циклов, нет ошибок ресурсов/API.
- Для синтетического /result/* и служебных маршрутов серверный noindex; в sitemap нет этих URL. Реальные capability-ссылки не используются в отчёте и сторонних валидаторах.
- Основной публичный текст, H1, ссылки, корректные lang/title/description/canonical присутствуют в исходном HTML; метаданные не становятся противоречивыми после hydration/навигации.
- JSON-LD валидна и соответствует видимому контенту, logo/favicon доступны; нет обещаний диагноза и вымышленных авторов/контактов.
- Главная, форма ввода, загрузка синтетического PDF и результат работают после изменения routing; медицинская логика не меняется. При изменении её поведения — отдельные граничные regression tests.
- Проверены mobile/desktop и клавиатурная навигация. Core Web Vitals измерены до/после, численные цели уточняются по baseline.
- По затронутым слоям выполнить client build/lint, nginx -t и релевантные backend проверки; не запускать backend lint с --fix.
- После разрешённой поставки повторить проверки на production и в инструментах вебмастеров; успешная сборка не заменяет проверку опубликованного HTML.
- git diff --check и git status --short; никаких secrets, дампов, реальных медицинских данных и generated build artifacts в diff.

## Риски и откат

Ошибки allowlist маршрутов могут сломать deep links; SSR/prerender может повлиять на hydration, i18n и загрузку справочников. Проверять на отдельной среде, не запуская одновременно локальные dev/prod-compose с конфликтующими именами и портами. Ошибочный глобальный noindex закроет публичные страницы — обязательно проверить матрицу заголовков.

Публиковать по этапам. Откат: вернуть предыдущие client/proxy artifacts и конфигурацию, проверить nginx -t, HTTP и форму. Изменений БД в исходном плане нет. Публикацию медицинского контента выполнять только после редакционной проверки; сроки переобхода и индексации не гарантировать.

## Уточнение реализации этапа 1 — 2026-10-26

Пользователь разрешил реализацию только этапа управления индексацией: robots/sitemap, серверный noindex, 404, www и /analysis redirects. Метаданные/canonical самостоятельных страниц, медицинский контент и рендеринг относятся к следующим этапам и здесь не меняются.

Сохраняем известные публичные SPA-маршруты и перечисленные admin endpoints, одноуровневый /result/:resultId, /logout и /test. Неизвестные URL получают 404 с оболочкой SPA, чтобы React показал текущую страницу ошибки; запросы отсутствующих статических ресурсов также 404. Для admin/results/logout/test/ошибок — X-Robots-Tag: noindex; для API — noindex на proxy. robots не блокирует эти HTML-маршруты, чтобы робот мог увидеть noindex; он не защищает доступ к данным.

Sitemap на первом этапе содержит только главную: у остальных публичных страниц пока canonical главной и/или шаблонный контент. Расширить карту после исправления метаданных и контента, не публиковать заведомо неканонические URL.

Production client Nginx реализует строгую матрицу путей; внешний proxy обеспечивает HTTP→HTTPS и HTTPS www→основной хост с фиксированным целевым доменом и сохраняет URI/query. /analysis и /analysis/ получают 301 на / с сохранением query. Для переходов внутри SPA /analysis заменяется Navigate с сохранением search/hash. Dev Vite остаётся dev-сервером; серверные статусы проверяются на изолированном production client Nginx, не на Vite.

Проверки: воспроизведение исходных дефектов; client build/lint; интеграционный HTTP harness против реального Nginx с синтетическим статическим build; проверка proxy с временным self-signed сертификатом только внутри изолированного контейнера, без обращения к production и без его перезапуска. Проверить redirects, query/hash, content types, noindex на 200/404/304 и отсутствие глобального noindex, глубокие ссылки, отсутствующие файлы, sitemap XML и assets. Не запускать полный production-compose и не подключать тестовый proxy к рабочей БД. Откат — прежние client image/proxy config, БД не меняется.

## Уточнение: canonical самостоятельных страниц — 2026-10-26

Пользователь разрешил отдельное исправление canonical. Страницы: /, /about, /contacts, /privacy-policy, /consent-personal-data. Для query/fragment и завершающего / указываем чистый HTTPS URL без query/hash и без завершающего / у внутренних страниц. /analysis остаётся redirect на /. Служебные страницы/результаты/404 не объявляются дублями главной и не получают canonical, noindex сохраняется.

Решение без SSR: после Vite build формировать несколько HTML-оболочек из общей сборки, меняя только canonical. Nginx отдаёт нужную оболочку по публичному маршруту; для служебных путей/ошибок отдельная оболочка без canonical. Общие JS/CSS и существующий контент не дублируются в исходниках. Единственный список публичных canonical routes используется генератором и React hook; при SPA-переходах hook синхронизирует один тег и удаляет его на служебном/неизвестном пути. Удалить статические hreflang на главную: для одноязычного сайта они необязательны и на внутренних страницах противоречат выбранной странице.

До реализации добавить HTTP regression cases на правильный canonical в исходном HTML, query/trailing slash, отсутствие canonical для noindex/404. После: build/postbuild, lint, все routing checks, браузерная проверка первоначального открытия и SPA-переходов. Sitemap пока не расширять: качество контента остаётся отдельной задачей. Lang/title/description/JSON-LD/favicon в этой правке не изменяются. БД/API не меняются. Публикация не входит в текущее локальное исправление; при поставке использовать более свежую production-базу и сохранить её изменения, как при этапе 1. Rollback требует согласованного возврата client build и client Nginx config, поскольку схема оболочек меняется.

## Метаданные, lang, изображения, JSON-LD — 2026-10-26

Пользователь разрешил следующий пункт: lang=ru, согласованные title/description в исходном HTML и DOM, рабочие favicon/logo, корректная JSON-LD без обещания «точной диагностики». Это локальная реализация без автоматической поставки/коммита.

Выбран единый источник metadata и общий генератор head для build и React. Использовать существующие route-specific оболочки: публичные страницы получают свои title/description/canonical и JSON-LD WebPage/AboutPage/ContactPage; результаты/служебные страницы — нейтральные title/description без JSON-LD и персональных URL; 404 — соответствующие метаданные. Устранить конкурирующие page-level useDocumentTitle: один владелец head обновляет его по pathname при SPA-навигации, включая Back. Query/hash/данные анализов не участвуют в метаданных.

Разметка только о фактически существующем сайте/странице: Organization/WebSite/WebPage с постоянными @id, корректным URL логотипа /pa.svg, inLanguage=ru; без MedicalDiagnostics, устаревшего aspect, вымышленных врачей/адресов/оценок/medical authority. Тексты title/description описывают справочное сравнение с референсами, не обещают диагноз. About/contacts описывать без вымышленных редакционных гарантий; их видимый шаблонный контент остаётся отдельным этапом.

Проверить favicon/logo HTTP GET/HEAD и MIME, валидность SVG, отсутствие блокировки robots; обеспечить читаемость статических файлов nginx worker в финальном client image. Существующий SVG не перерисовывать. Пути в metadata и JSON-LD должны совпадать, /public/pa.svg не использовать.

До реализации добавить regression cases на язык, page-specific title/description, согласованную JSON-LD и загрузку icon/logo. После: build/postbuild, lint, полный Nginx harness, проверка собранного production image (не только dist mounts), browser initial/SPA/Back/service/404. Внешние валидаторы могут проверяться только на синтетическом публичном HTML без результатов/секретов; гарантии rich results не даются. БД/нормативы/API не меняются. Rollback — предыдущий client image; обновлённые оболочки и client Nginx поставляются вместе. Для последующей публикации сохранить более свежую production-базу и её зависимости.

## Рендеринг публичного контента — 2026-10-26

Пользователь разрешил реализацию этапа рендеринга. Выбран build-time prerender/SSG на существующих React/Vite: пять public paths из allowlist, без Node server в production и без сети/БД в сборке. SSR entry рендерит тот же AppContainer через StaticRouter и новый пустой Redux store на каждую страницу. Персональные пути/служебные endpoints SSR entry отвергает; их HTML остаётся пустой CSR-оболочкой с noindex, без preloaded state/JSON результатов. Server bundle расположен вне dist и не копируется в runtime image.

Границы hydration: статическая публичная часть (навигационная guest-оболочка, H1/описание/категории, about/contacts/документы, footer) совпадает между server HTML и первым client render. Browser-only зоны — форма с select/dropzone, авторизация, cookie-баннер и модальные окна — включаются после hydration через ClientOnly/useSyncExternalStore. Никаких window/localStorage polyfills в сборке, suppressed hydration warnings или обхода авторизации. Публичные React-компоненты не заменяются отдельным SEO-текстом.

Выделить форму главной из статического содержимого, сохранить её Redux/actions/валидацию/загрузку PDF. До JS показывать понятное сообщение о необходимости JS для формы. Публичные аккордеоны перевести на native details/summary, чтобы список и текст можно было раскрывать без JS; сохранить визуальный стиль и multiple-семантику. Добавить обычные внутренние ссылки public pages в footer. About/contacts/политики не редактировать медицински/юридически: известные шаблоны и несоответствия остаются редакционным этапом и должны быть проверены до контентного продвижения.

Сборка: Vite client build, отдельный SSR build вне dist, генератор metadata+body только public paths, в HTML marker для hydrateRoot; для CSR-only путей createRoot. Dev transformIndexHtml использует тот же SSR entry через ssrLoadModule, чтобы проверять hydration локально. Инициализацию i18n и обращения к справочникам оставить только browser-side после ClientOnly; static labels берутся из уже существующего публичного текста.

Проверки: до реализации воспроизвести пустой body; HTTP H1/смысловой текст/ссылки всех public pages без JS; отсутствие prerender на результатах/admin/404 и недоступность SSR bundle; предыдущие metadata/routing tests. SSR entry tests reject private/unknown paths; запрет сетевых обращений при рендеринге, независимость пустых store. Browser: hydration без recoverable errors, нативный accordion, SPA/Back, mobile/desktop, ручная валидация формы без сохранения; синтетический PDF/PDF response flow — без реальных документов и записи в рабочую БД. Никаких health-only выводов о версии. Build/lint и изолированный Nginx runtime check, git diff --check/status.

БД/API/нормативы не меняются. Перед работой создан и проверен локальный backup в игнорируемом sqlDump. Публикация/коммит — отдельным запросом. Откат — предыдущий client image; builder server bundle и runtime dist не смешивать. CWV/CrUX не доступны из локальных unit checks, полевых улучшений не обещать.

### 2026-10-26 — скачок при гидратации
Воспроизведение в коде: ClientOnly заменяет FormPlaceholder фиксированной приблизительной высоты реальной формой; sticky cookie-баннер добавляется в поток после гидратации. Решение: рендерить начальную пустую форму в HTML, сделать select SSR-совместимыми со стабильными ID, не приостанавливать форму ради переводов, вывести cookie-баннер поверх страницы. Проверка: сборка, SSR без сети, lint, браузер. БД и медицинские расчёты не меняются; ранее проверенный backup сохраняется.

### 2026-10-26 — размер SVG в header до CSS
У SVG логотипа и публичных пунктов header нет атрибутов width/height; Tailwind задаёт размер только после CSS. Добавить intrinsic размеры, сохранив responsive классы. Regression: каждая SVG публичного header должна иметь положительные width/height в SSR HTML. БД не меняется, проверенный backup задачи сохранён.

### 2026-10-26 — CSS до первого отображения
Уточнение: Vite dev инжектирует импортированный из main.tsx CSS через JS, что даёт FOUC при SSR HTML. Перенести оба глобальных CSS в link rel=stylesheet в head; Vite обрабатывает их и при build. Проверить dev HTML и content-type CSS, собранные ссылки, lint/SSR.

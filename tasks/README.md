# Рабочие задачи

Каждую отдельную задачу, затрагивающую логику работы приложения, веди в собственном каталоге `tasks/`.

Организационные изменения, которые не меняют поведение приложения, в `tasks/` не оформляй. К ним относятся правки инструкций и документации о процессе работы, служебных шаблонов и прочих правил ведения репозитория.

## Структура и нумерация

- Имя каталога начинается с четырёхзначного порядкового номера: `tasks/0001-short-description/`, `tasks/0002-short-description/` и далее.
- Используй следующий номер после максимального существующего префикса; удалённые и пропущенные номера не переиспользуй.
- Short description пиши латиницей в kebab-case и отражай результат, а не номер тикета без контекста.
- В каталоге храни описание решения и только обезличенные небольшие fixtures, относящиеся к задаче.
- Не клади в `tasks/` PDF пациентов, дампы БД, `.env`, пароли, токены, result links/IDs, email, извлечённый медицинский текст, реальные значения анализов или логи с такими данными.

## Обязательные файлы

### `plan.md`

Создаётся до изменения приложения или БД и содержит:

- цель и границы задачи;
- наблюдаемое и ожидаемое поведение;
- текущую реализацию и подтверждающие ссылки на код;
- выбранное решение и отвергнутые варианты, если выбор неочевиден;
- этапы и затрагиваемые файлы/API/таблицы;
- влияние на приватность, безопасность и медицинскую интерпретацию;
- миграцию и rollback, если меняется схема/данные;
- риски, критерии приёмки и план проверки.

### `status.md`

Ведётся в процессе работы. Для каждого этапа фиксируй статус, сделанное, принятый результат, оставшуюся работу и выполненную проверку. Допустимые статусы: `не начат`, `в работе`, `на проверке`, `принят`, `заблокирован`.

Этап нельзя отмечать как `принят` без записанного результата и проверки. Если решение изменилось, не переписывай историю молча: добавь дату, причину и новое решение.

### `implementation.md`

Создаётся после завершения или принятия реализации и содержит:

- итоговое поведение и ключевые изменения;
- изменения API, схемы, данных и конфигурации;
- порядок миграции и rollback;
- ограничения и осознанно оставшийся технический долг;
- тесты, smoke checks и результат проверки;
- инструкции по безопасной поставке, если они требуются.

## Порядок работы

1. Выполни `git status --short`, изучи пользовательские изменения и ограничь diff текущей задачей.
2. До создания файлов задачи и любых изменений сделай дамп локальной БД. Сохрани его в игнорируемом Git каталоге `sqlDump/`, проверь, что дамп читается, и не выводи его содержимое или чувствительные данные в терминал, документы задачи и ответы.
3. Создай каталог задачи, `plan.md` и начальный `status.md`. В `status.md` зафиксируй только факт создания и успешной проверки дампа без его содержимого.
4. Для дефекта сначала добавь минимальный regression test или зафиксируй воспроизведение, если тест пока невозможен.
5. Реализуй изменение небольшими проверяемыми этапами; после каждого обновляй `status.md`.
6. При изменении БД сначала выполни read-only diff/аудит. До записи покажи план, повторно убедись в наличии проверенного локального backup и получи явное подтверждение пользователя.
7. Проверь backend/client/Python только в затронутой области, затем выполни релевантные build, tests и smoke checks из корневого `AGENTS.md`.
8. Для медицинской логики проверь границы диапазонов, age/gender/unit и отрицательные сценарии. Используй синтетические данные без связи с реальными людьми.
9. Выполни `git diff --check` и `git status --short`; убедись, что в diff нет secrets, PDF, дампов, логов и generated artifacts.
10. Обнови `implementation.md`, а этапы в `status.md` переведи в `на проверке` или `принят` согласно фактическому состоянию.

## Изменения данных и опасные операции

Без отдельного плана, резервной копии и явного подтверждения не выполняй:

- migrations/DDL и восстановление дампа;
- массовые UPDATE/DELETE, очистку результатов или sessions;
- пересчёт нормативов и текстов интерпретаций;
- импорт реальных PDF или production-данных;
- запуск скриптов с `--fix`, если они могут затронуть файлы вне задачи;
- обращения локальных сервисов к production БД или внешним endpoint.

SQL для исследования по умолчанию должен быть read-only и возвращать схему или агрегаты. В `plan.md` и `status.md` сохраняй обезличенный смысл результата, а не полный вывод, если он может содержать чувствительные значения.

## Проверка по слоям

- Server: unit/integration test, `npm run build`, health API и негативная проверка authorization для защищённых маршрутов.
- Client: `npm run build`, lint и ручной smoke test изменённого маршрута в dev-контейнере.
- Python/PDF: compile/import check, `/health`, синтетический PDF fixture, лимиты размера/страниц/времени и отсутствие извлечённого текста в логах.
- DB: миграция на копии, constraints/indexes, row counts до/после, повторный запуск (идемпотентность) и rollback.
- Сквозной поток: ввод/загрузка → проверка распознанных данных → сохранение → открытие result link, без публикации самой ссылки.

В ответах по задаче указывай её каталог. Большие описания конкретной реализации не дублируй в корневом `AGENTS.md`.

## Согласованная цель

Распознавать и показывать исходные значение/единицу документа. Для каждого показателя выбрать одну расчётную единицу из существующих нормативов, хранить нормативы только в ней. Сервер переводит исходное значение в расчётное для всех сравнений/интерпретаций. Клиент показывает результат и обратнопереведённые min/max в исходных единицах. Первый этап — только проверенные линейные преобразования с постоянным положительным коэффициентом, без mass↔molar, offsets, нелинейных формул и percent↔absolute count. Не является медицинским диагнозом.

## Подтверждённая отправная точка

- server/src/analysisPointUnits/analysisPointUnits.model.ts: units имеют только id/name, нет DB aliases/conversion rules.
- server/src/analysisResult/pdf-unit-parser.ts: временный словарь spelling/equivalence в коде; только разрешённые point units, без масштабирующих коэффициентов.
- server/src/analysisResult/analysisResult.service.ts: save использует value/unit как пришли; getMin/getMax вызываются без unitId. Сохранение parent/children пока без общей транзакции.
- server/src/analysisPointMinValue и analysisPointMaxValue: нормы зависят от point/age/gender/unit. Нельзя выбрать единственную расчётную unit до проверки существующих нескольких наборов/противоречий.
- client/src/entities/analysisResult/model/slice.ts: после PDF unit из findings сейчас отбрасывается и units задаётся пустой строкой.
- DB gold pointId/name/value/unit/unitId уже представляет исходные значения, не нормализованные; Python и sources не менять.

## Модель данных и правила

1. Расширить analysisPointUnits стабильным кодом (ориентир UCUM) и полем translationParsing со строкой обозначений через `_`, аналогично параметрам; сохранить существующие ID/name. По согласованному уточнению пользователя отдельную таблицу aliases не создавать. Пример для g/dl: `г/дл_g/dl_g/dL_г/100мл`. В одном поле только обозначения одной единицы, не g/l и g/dl вместе. Общую нормализацию пробелов, micro/Unicode степеней и разделителей оставить коду, не перечислять все комбинации пробелов в БД. Нельзя безусловно приводить обозначения к нижнему регистру: префиксы могут менять смысл. Проверять пустые варианты/дубли и межъединичные коллизии при подготовке, изменении и загрузке справочника; неоднозначность не разрешать порядком записей. Уникальность отдельных вариантов внутри строки обеспечивается прикладной валидацией, обычного UNIQUE по translationParsing недостаточно. RU/EN обозначения одной единицы не являются отдельными units; преобразования разных единиц остаются в отдельной таблице правил.
2. Добавить calculationUnitId к analysisPoint. Одна расчётная unit на показатель; её наличие/разрешённость и наличие нормативов проверяются. Существующая analysis_point_units задаёт допустимые единицы ввода, включая новые g/dl для нужных показателей, но не даёт разрешения применять их к любому point.
3. Таблица проверенных conversion rules: fromUnitId, toUnitId, coefficient DECIMAL, version, active, при необходимости pointId для ограничения применимости. На первом этапе только from→calculationUnit прямые правила, не поиск произвольных цепочек. Проверки положительного конечного коэффициента, совместимости величин, отсутствия неоднозначных активных правил. Identity k=1 явно поддерживается. Изменение коэффициента — новая версия, не переписывание использованной версии. Глобальный физический коэффициент можно переиспользовать для разрешённых point, но сама допустимость ввода всегда point-specific.
4. Хранить sourceValue/sourceUnitId/sourceUnitText, calculationValue/calculationUnitId и ссылку/снимок версии применённого коэффициента. Текущие value/unitId остаются совместимым расчётным представлением либо получают явный compatibility mapping в DTO; точное полевая схема фиксируется в реализации до миграции, без двух расходящихся числовых источников истины. Предпочтение: value/unitId = расчётное, source* = исходное, conversionRuleId + appliedCoefficient = provenance.
5. Сохранять исходное написание отдельно от канонического DB label: UI показывает распознанное/выбранное исходное обозначение, а не заменяет его расчётным. Свободный sourceUnitText не участвует в расчётах и не логируется; ограничить длину и безопасно отображать как текст.
6. Старые результаты не переписывать при изменении коэффициентов. Историческое значение считается известным только в сохранённой unit; исходный PDF spelling не реконструировать. Любой backfill — отдельный dry-run и подтверждённый этап. Изменение исторических нормативов/клинических текстов вне задачи.

## Этапы реализации

### 1. Read-only аудит и утверждение справочника

Составить обезличенный список units, point→units, единиц существующих min/max, конфликтов и дублей. Предложить calculationUnitId каждого point, список новых units, значений translationParsing и коэффициентов. Первый проверочный пример — гемоглобин g/dl→g/l, k=10; также identity и уже используемые численно равнозначные записи k=1. Не объединять дубли/не удалять нормы автоматически. Показать точный DB diff/row counts и спорные случаи на утверждение.

### 2. Версионированная миграция БД

Аддитивно добавить schema/FK/checks/unique indexes, справочник и утверждённые rules. Decimal precision выбрать по аудиту диапазона значений, хранить коэффициенты без binary float. Миграция транзакционная и идемпотентная, с проверяемым rollback. Не запускать обычный Nest bootstrap для аудита: он выполняет startup migrations. Перед любым DDL/DML — свежий проверенный backup, отдельное явное подтверждение точного плана, dry-run на копии, проверки counts/constraints/rollback. Не создавать новые нормативы для каждой исходной unit. Консолидация существующих многовариантных нормативов допускается только по отдельно утверждённой семантике; до этого не выбирать первую запись.

### 3. Серверный сервис единиц и преобразования

Единый сервис: resolve spelling→sourceUnitId; validate point/sourceUnit; resolve direct rule→calculationUnit; normalize sourceValue; inverse-convert границы для отображения. Только decimal arithmetic, без округления до сравнения; политика отображаемой точности задаётся отдельно и не меняет классификацию. Проверки NaN/Infinity/переполнения/нулевого и отрицательного k, неизвестных units/rules, несовместимых величин. Не доверять коэффициенту/расчётному значению от клиента, не делать сетевые вызовы для преобразования медицинских значений.

### 4. PDF parsing и ручной ввод

Заменить runtime unit dictionary обозначениями из analysisPointUnits.translationParsing; отдельную таблицу aliases не использовать. Канонический code/name также участвует в поиске, если однозначен. Структурное выделение unit рядом с выбранным результатом оставить. Возвращать исходные value/unitId/unitText; при наличии утверждённого правила можно дополнительно возвращать расчётное представление явно отдельными полями. Не подменять единицу без преобразования значения. Неизвестное/неоднозначное evidence остаётся null с reason code; пользователь выбирает единицу. Python не менять, request-local state сохранить.

### 5. Сохранение, нормативы и интерпретации

DTO явно разделяет исходные и расчётные поля; canonical result пересчитывает только сервер. До записи проверить весь набор. Parent/children/source/calculation/provenance сохранять общей транзакцией, без молчаливого пропуска invalid points. Если правило/единица не определены — понятная validation error без частичного сохранения, клиент предлагает исправление; не выдавать статус NORMAL по умолчанию. Lookup min/max везде pointId+ageId+genderId+calculationUnitId; тем же нормализованным значением/единицей пользоваться в условиях текстовых интерпретаций. При отсутствующей/неоднозначной норме — явный статус «нет интерпретации», не выбирать произвольную границу.

### 6. Клиент

После PDF заполнять source value и unit из ответа, сохраняя возможность ручного исправления. При смене единицы не умножать значение повторно: выбранная единица интерпретирует введённое значение, расчёт делает сервер. Формы/PDF используют один механизм. На результате показывать исходные значение/единицу и min/max в той же unit (minCalculation/k, maxCalculation/k). Статус/интерпретация — серверные по неокруглённым canonical данным. Расчётное представление доступно отдельным пояснением. Выводить неизвестные units/rules и отсутствие нормативов без медицинских предположений. Старые response/сохранённые результаты поддержать compatibility path без молчаливой смены unit.

### 7. Методология и тесты

- Сохранить prepared Python/sources без изменений. DB gold ожидает исходный pointId/value/unitId; коэффициенты не должны подменять ожидаемое распознавание. Корректировки старых null-unit gold — только отдельным явным запросом и предметной проверкой.
- Synthetic conversion tests: g/dl→g/l и обратно, k=1, разные единицы одного point, неразрешённые point/unit, неподдерживаемые правила/величины, ноль/отрицательные/NaN/overflow, decimal comma/dot.
- Synthetic parsing tests: translationParsing с RU/EN обозначениями, пустые элементы/дубли/коллизии разных units, значимый регистр префиксов, нормализация Unicode/пробелов, g/dl и g/l как разные unit identities. Конфликтующий alias не должен давать произвольную единицу даже при единственном разрешённом варианте у point.
- Нормативы: ровно min/max и сразу ниже/выше, одна классификация для эквивалентных исходных единиц, пол/возраст, отсутствие/дубли нормативов; сравнение без преждевременного округления.
- Сохранение: атомарность, провал посередине, provenance, защита от присланных canonical value/coefficient, изменение версии правила без пересчёта истории, старые данные без source fields.
- UI: заполнение unit после PDF, ручная смена, запрет двойного пересчёта, исходные units и обратно переведённые min/max, безопасный текст, понятные ошибки.
- Все18 Nest prepared cases и unit/triple отчёт по установленной методологии; никаких frozen snapshots/ID manifests/автогенерации gold. Runtime DB translationParsing не является тестовой фиксацией.
- Backend tests/build; client build/lint и smoke; DB dry-run/constraints/counts/repeat/rollback; health. Чувствительные payload/значения/ссылки не выводить, auth поверхность не расширять.

### 8. Поставка и rollback

Expand→проверенные rules→совместимый backend→client→поэтапное включение. До включения обнаружить старые clients и обеспечить единый серверный путь нормализации без двойного умножения. Отдельно проверить source/result DTO совместимость. При rollback отключить нормализацию и вернуть совместимую версию приложения; не удалять source/provenance и не читать calculationValue как sourceValue. Обратимость старого клиента с новыми данными проверить заранее; полный DB restore — только отдельно согласованная крайняя мера после учёта новых записей.

## Приёмка и границы согласования

Для synthetic примера12 g/dl клиент показывает12 g/dl; сервер сравнивает120 g/l с единственным нормативом g/l; показанные min/max приведены в g/dl. Эквивалентный ввод в g/l даёт тот же статус. Источник и правило воспроизводимы после изменения справочника. Нельзя получить интерпретацию с неразрешённой/неизвестной единицей, выбрать min/max без unitId или сохранить половину результата. Существующие point/value результаты не регрессируют; ограничения gold показаны честно.

Сейчас требуется согласование этого плана для начала реализации. Оно не заменяет обязательное отдельное подтверждение конкретной миграции/изменений локальной БД и backfill после этапа1. Ветка/коммит/пуш по отдельному запросу; не смешивать незавершённые изменения0001 с новой реализацией.

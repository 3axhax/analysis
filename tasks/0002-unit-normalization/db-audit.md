# Read-only аудит перед нормализацией единиц

Уточнение после аудита: предложение закрепить 63 calculation units и исключить четыре показателя отменено пользователем. Реализован выбор интервала по point/age/gender с приоритетом исходной unit и проверкой конвертируемых альтернатив. Таблица ниже — исторический аудит, не инструкция консолидировать нормативы.

Дата:2026-10-15,16:32 UTC+05:00. Реализация начата с этапа1 согласованного плана. Свежий backup локальной БД создан и проверен. Все запросы выполнялись в BEGIN TRANSACTION READ ONLY, через уже работающий PostgreSQL контейнер; Nest bootstrap/migrations не запускались. Персональные результаты и значения анализов не читались.

## Подтверждённое состояние

-67 показателей,15 units,71 point→unit связи;1898 min и1898 max записей.
-63 показателя имеют ровно одну единицу в совокупности min/max; это кандидат calculationUnitId, а не разрешение менять нормативы.
-4 показателя имеют разные единицы нормативов, перечислены ниже. Нормативов без разрешённой point→unit связи не выявлено.
-Два дублированных ключа min у ggtp/unit12;2 контекста min>max. Эти аномалии вне автоматического исправления задачи.
-Сохранённый value имеет тип double precision. Для новых расчётов нужна отдельная авторитетная decimal величина либо явно согласованное изменение value; исторические float-значения автоматически не пересчитывать.
-Клиент PDF reducer отбрасывает возвращённую unit; это будет исправлено на клиентском этапе, не заменяет необходимость server validation.

## Предлагаемая область первой миграции — требует отдельного подтверждения

1. Добавить nullable calculationUnitId(FK units) в analysisPoint; заполнить только63 однозначных кандидата, для4 спорных оставить null с явным режимом normalization unavailable. Нормативы не изменять. После отдельного предметного решения заполнить остальные4.
2. Добавить code/translationParsing в15 существующих units, не менять существующие ID/name. Каждой unit задать только её собственные обозначения, с case-sensitive collision validation. Численно равные, но разные DB units (например ng/ml и mkg/l) сохранять отдельными: переводить утверждённым k=1, не дублировать один alias на обеих.
3. Добавить одну новую unit g/dl и2 связи ввода: hemoglobin(id1), mchc(id10), у обоих calculation unit g/l(id2). Прямое правило g/dl→g/l,k=10. Identity k=1 поддержать явно без произвольного пути конверсий. Остальные масштабные переходы — только после утверждения списка; mass↔molar и percent↔absolute отсутствуют.
4. Добавить версионированную таблицу правил conversion (from/to unit, coefficient decimal>0, version, active; applicability ограничена point→unit), ограничения неоднозначного активного правила и неизменяемость использованной версии.
5. Добавить nullable source/provenance/decimal calculation поля в analysisResultPointData; не выполнять backfill/пересчёт старых результатов и не удалять существующие value/unitId. Конкретный DDL/decimal precision зафиксировать перед dry-run; новые расчётные поля — авторитетные, старые value/unitId только совместимое представление. Source поля включают value/unitId/unitText, provenance — rule id и applied coefficient. Старые записи читаются через явный legacy fallback.
6. Не удалять/объединять4 спорных набора норм, дубли ggtp или reversed ranges. Не изменять users/sessions/результаты/данные0001. Новые нормы для g/dl не создавать.

Это предложение области изменений, не выполненная миграция. До DDL/DML нужен точный миграционный diff, проверка constraints/counts и rollback на копии, свежий backup и явное подтверждение пользователя. Для спорных показателей рекомендуемый временный режим — сохранить историю без автоматического пересчёта, не выдавать новую интерпретацию при неутверждённой calculation unit.

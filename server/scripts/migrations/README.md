# Миграции единиц и результатов

Доставка up осуществляется существующим `MigrationsService.onModuleInit()`:

1. Старые entity migrations.
2. `MigrationsAnalysisPointUnits.addUnitNormalization()` — marker `0002-unit-normalization`.
3. `MigrationsAnalysisPointUnits.addFerritinSourceUnit()` — marker `0003-ferritin-source-unit`.
4. `MigrationsAnalysisResult.allowSourceOnlyMeasurements()` — marker `0006-source-measurements`.

SQL находится в `server/src/migrations/unit-migrations.sql.ts` и компилируется в dist. Ручных up-файлов больше нет. Существующие markers совместимы, обновлённые БД не изменяются повторно. Каждая новая миграция использует транзакцию для DDL/seed/marker и advisory lock для конкурирующих запусков. Ошибка останавливает startup, а не пропускает миграцию. Каталог единиц при первом0002 должен соответствовать проверенной исходной конфигурации; при расхождении предусмотрен отказ, не автоматическая подмена данных.

До поставки нужны проверенный backup, согласование изменения схемы и проверка на копии. Автостарт — способ доставки, не разрешение запускать изменения production без этих условий.

Оставшиеся `.down.sql` — только явно согласованный rollback. Остановить новую версию, затем рассматривать откат в обратном порядке0006→0003→0002; следующий запуск новой версии восстановит удалённые markers. Скрипты отказывают при наличии использующих новые поля/единицы данных. Не удалять измерения для обхода защиты. `.verify.sql` допускается только на disposable копии и создаёт синтетические тестовые записи.
